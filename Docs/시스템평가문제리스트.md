# 시스템 평가 문제 리스트

> 평가 단위: `Assets/1.Code/Scripts/` 아래 **폴더 하나 = 시스템 하나** (PlayerSystem은 그 안의 하위 폴더가 시스템 단위)
> 전제: 각 시스템은 **통째로 들어내고 다른 걸로 갈아 끼울 수 있어야 한다**
> 제외: `Old/`, `_Test`, `Test_`
> 상태: 미확정 (문제 제기까지만. 코드는 아직 안 고침)

---

## 이 문서를 읽는 법

각 문제는 세 줄로 되어 있음.

- **문제**: 게임을 하다 실제로 겪게 되는 증상
- **원인**: 코드에서 무엇이 무엇을 했기 때문인지
- **해결**: 어떻게 바꾸면 되는지

"교체 불가"라는 말이 자주 나오는데, 뜻은 이거임.
**A 시스템 코드 안에 B 시스템의 클래스 이름이 박혀 있으면, B를 갈아 끼울 때 A도 같이 뜯어고쳐야 함.**
콘센트 규격(인터페이스)에 꽂아야 하는데 전선을 직접 납땜해 둔 상태라고 보면 됨.

---

## 1. Animation

### 1-1. 캐릭터를 못 찾으면 애니가 조용히 멈춤

- **문제**: 이동 애니메이션이 안 나오는데 콘솔에 에러 한 줄도 안 뜸. 어디가 고장인지 알 수가 없음.
- **원인**: `SetAnimator`가 캐릭터를 못 찾으면 아무것도 안 하고 그냥 넘어감(PlayerMoveAnimation.cs:67-73). 그래서 `_animator`가 null인 채로 남고, `Update`는 null이면 조용히 return(:36).
- **해결**: 캐릭터를 못 찾은 시점에서 `Debug.LogError`로 알림. 조용히 실패하는 코드는 버그를 숨기는 코드임.

### 1-2. 상태가 정상 종료되면 예외가 터짐

- **문제**: 특정 상황(캐릭터를 못 찾은 상태에서 이동 구간이 끝날 때) NullReferenceException이 뜸.
- **원인**: `Update`는 `_animator == null`을 검사하는데(:36), `HandleClose`는 검사 없이 바로 `_animator.SetFloat`을 부름(:64).
- **해결**: `HandleClose`에도 같은 null 검사를 넣음. 더 나은 방법은 1-1을 고쳐서 애초에 null이 안 되게 하는 것.

### 1-3. 다른 시스템 클래스를 그대로 갖다 씀 → 교체 불가

- **문제**: States·Data·Character 시스템 중 하나만 바꿔도 Animation이 컴파일 에러가 남.
- **원인**: `StateEventCategory`(States), `IStartData`·`CloseEventType`(Data/States), `PlayerCharacter`(Character)를 코드에 직접 적어 씀(:31, :53, :59, :67).
- **해결**: "지금 이동 중인가"만 알려주는 인터페이스 하나(`IMoveAnimationGate` 같은)를 Animation 폴더에 두고, 그것만 주입받음. 남의 enum·클래스는 그 인터페이스 뒤로 숨김.

### 1-4. Character 시스템 속을 두 단계 파고듦

- **문제**: Character 시스템이 컴포넌트 보관 방식을 바꾸면 Animation이 깨짐.
- **원인**: `CurrentCharacter`를 받아서(→1단계) 다시 `GetCharacterComponent<Animator>()`를 부름(→2단계) (:55, :71).
- **해결**: Character 쪽이 `IAnimatorProvider`처럼 "Animator 하나 줘" 인터페이스를 내주고, Animation은 그것만 받음.

## 2. Audio

### 2-1. 발소리가 애니메이터 파라미터 이름에 몰래 묶여 있음

- **문제**: Animation 시스템에서 파라미터 이름을 `MoveX`→`InputX`로 바꾸면, 발소리만 조용히 안 남. 에러도 없음.
- **원인**: `FootstepEmitter`가 `Animator.StringToHash("MoveX")`로 문자열을 직접 박아 읽음(FootstepEmitter.cs:29-30). 두 시스템이 **문자열로 몰래 약속**한 상태임.
- **해결**: 이동 방향은 Animation(또는 Movement)이 값으로 알려주게 함. 파라미터를 훔쳐보지 말고 받아야 함.

### 2-2. 채널·애니메이터가 없으면 무음인데 아무 표시가 없음

- **문제**: 발소리가 통째로 안 나는데 원인을 찾을 단서가 없음.
- **원인**: `_channel == null || _animator == null`이면 그냥 return(FootstepEmitter.cs:49-52). 로그 없음.
- **해결**: `Awake`에서 한 번 검사하고, 없으면 `Debug.LogError` 후 컴포넌트를 꺼버림. 매 프레임 조용히 참는 것보다 낫음.

### 2-3. 상태 데이터 타입을 직접 씀 → 교체 불가

- **문제**: Data/States 시스템을 바꾸면 Audio도 같이 수정해야 함.
- **원인**: `IPlayerAudio`, `IStartData`, `StateEventCategory`, `CloseEventType`을 직접 사용(PlayerAudioHandler.cs:21,25,40).
- **해결**: Audio 폴더 안에 "이 소리를 이 타이밍에 켜라"는 자체 요청 타입을 두고, 상태 시스템 쪽에서 그 타입으로 변환해 보내게 함.

## 3. Character

### 3-1. 없는 컴포넌트를 계속 찾으며 에러 로그를 반복함

- **문제**: 캐릭터에 `Animator`를 안 붙였을 때, 상태가 바뀔 때마다 같은 에러가 계속 쌓임.
- **원인**: `GetCharacterComponent`가 **못 찾은 결과(null)도 캐시에 저장**함(PlayerCharacter.cs:20). 다음에 불러도 캐시에 null이 있으니 또 `LogError`를 냄(:25).
- **해결**: 못 찾았으면 캐시에 넣지 않거나, 에러를 한 번만 내도록 "이미 경고한 타입" 집합을 둠.

### 3-2. 이 시스템이 게임 전체에 뿌리내려 있어 교체가 불가능함

- **문제**: `PlayerCharacter`를 다른 구조로 바꾸려면 CameraSystem, GimmickSystem, SaveSystem, 그리고 PlayerSystem 안 8개 폴더를 전부 고쳐야 함.
- **원인**: Character 시스템이 **인터페이스를 하나도 안 내놓고** 구체 클래스 `PlayerCharacter`를 그대로 외부에 노출함. 외부는 그걸 직접 적어 씀.
- **해결**: `ICharacterInfo`(종류 알려주기), `ICharacterComponents`(컴포넌트 주기)처럼 용도별 인터페이스를 만들고, 외부는 인터페이스만 주입받게 바꿈.

## 4. DamageReceive

### 4-1. 체력 시스템이 빠지면 플레이어가 절대 안 죽음

- **문제**: `PlayerHealth`를 안 붙이거나 주입이 실패하면, 아무리 맞아도 죽지 않는 무적 상태가 됨.
- **원인**: 체력이 없을 때 남은 체력을 `100`으로 가정하고 진행함(PlayerDamageReceiver.cs:59). 100은 0보다 크니 사망 분기로 절대 안 감.
- **해결**: 체력이 없으면 `Debug.LogError`로 알리고, 사망 판정 자체를 건너뛰는 게 아니라 "이 컴포넌트는 지금 반쪽짜리"임을 드러냄.

### 4-2. 사망 신호를 받으려면 구체 클래스를 알아야 함

- **문제**: 피격 처리 방식을 다른 걸로 갈아 끼우면 `PlayerDeathTrigger`가 바로 깨짐.
- **원인**: `PlayerDeathTrigger`가 `List<PlayerDamageReceiver>`라는 **구체 클래스 목록**을 주입받아 그 클래스의 이벤트를 구독함(PlayerDeathTrigger.cs:12,23).
- **해결**: `IPlayerDeathNotifier` 같은 인터페이스에 `OnPlayerDied`를 올리고, 그걸 주입받음.

### 4-3. 무적과 피격 쿨타임이 따로 놀아 무적 시간이 예측 안 됨

- **문제**: 슈퍼아머 중 다단히트를 맞으면 어떤 히트는 들어가고 어떤 히트는 씹힘. 기획 의도대로 데미지가 안 들어감.
- **원인**: 무적(`_invincible`)과 별개로 `_damageCooldown` 0.5초짜리 자체 쿨타임이 또 있음(PlayerDamageReceiver.cs:52). 규칙이 두 군데로 갈라짐.
- **해결**: "지금 데미지를 받을 수 있나"를 판단하는 곳을 한 군데로 합침.

## 5. Data

### 5-1. 이벤트 종류를 하나 늘리려면 파일 네 곳을 동시에 고쳐야 함

- **문제**: "화면 흔들기" 같은 새 연출을 추가할 때 빠뜨리는 파일이 생기고, 인스펙터에는 칸이 보이는데 아무 일도 안 일어남.
- **원인**: 종류 정보가 `StateEventCategory`(enum), `StateData`의 배열 필드, `BuildDataMap`의 등록 줄, 그리고 새 `~DataEntry` 이렇게 **네 군데로 흩어져 있음**(StateEventCategory.cs, StateData.cs:24-54).
- **해결**: 배열 필드 대신 `[SerializeReference]` 목록 하나로 모으거나, 최소한 카테고리 등록을 한 곳에서만 하도록 묶음.

### 5-2. 데이터 시스템인데 남의 시스템 타입을 계약에 박아 둠

- **문제**: 소리·이펙트 시스템을 바꾸면 데이터 정의까지 같이 수정해야 함.
- **원인**: `IPlayerAudio`가 `SoundType`(AudioSystem), `IPlayerEffect`가 `EffectId`(Effect), `IPlayerCameraShake`가 `ShakeData`(CameraSystem)를 직접 씀.
- **해결**: 지금 구조에선 사실상 불가피함. 대신 **"Data는 다른 시스템 타입을 담는 그릇"이라고 문서에 못 박고**, 그 외의 결합은 금지하는 쪽이 현실적임.

### 5-3. 인스펙터 값이 조용히 무시될 수 있음

- **문제**: SO에 값을 채웠는데 게임에서 아무 일도 안 일어남.
- **원인**: `GetData<T>()`가 타입이 안 맞는 배열은 경고 없이 건너뜀(StateData.cs:88-91).
- **해결**: 건너뛴 카테고리를 에디터에서만 `Debug.LogWarning`으로 알려줌.

## 6. Effect

### 6-1. 이펙트 풀이 바닥나면 연출이 조용히 사라짐

- **문제**: 연타하면 이펙트가 가끔 안 나옴. 게임은 멀쩡히 돌아가서 버그인 줄도 모름.
- **원인**: 풀이 비면 `Rent`가 경고 한 줄 남기고 null을 돌려주고(PlayerEffectProvider.cs:53-54), 받는 쪽은 null이면 그냥 return함(PlayerEffectHandler.cs:45-48). 기본 여유분은 3개뿐임.
- **해결**: 풀이 비면 하나 더 만들어 쓰도록(자동 확장) 바꾸거나, 카탈로그의 `PoolSize`를 실제 최대 동시 개수에 맞춰 올림.

### 6-2. 붙일 자리 key가 겹치면 나중 것이 조용히 이김

- **문제**: 이펙트가 엉뚱한 위치(다른 캐릭터의 손 등)에 나타남.
- **원인**: 씬에서 모은 부착점을 `_attachPoints[obj.Key] = obj.Transform`으로 덮어씀(PlayerEffectHandler.cs:32-34). 같은 key가 둘이면 뒤에 온 것이 이김.
- **해결**: 이미 있는 key면 `Debug.LogError`로 중복을 알림.

### 6-3. 씬을 나갈 때 이펙트가 켜진 채로 남음

- **문제**: 씬을 옮겼는데 이펙트가 화면에 남아 있거나, 다음 씬에서 이상한 게 보임.
- **원인**: `OnDestroy`가 코루틴만 멈추고 리스트를 비움. **인스턴스를 끄지도, 반납하지도 않음**(PlayerEffectHandler.cs:120-131).
- **해결**: `OnDestroy`에서 남은 이펙트를 전부 `SetActive(false)` 후 반납함.

## 7. Finish

### 7-1. 적 시스템에 통째로 못 박혀 있음

- **문제**: 적 클래스를 바꾸면 처형 기능이 통째로 깨짐. 처형만 따로 재사용하는 것도 불가능함.
- **원인**: `Enemy`·`CaliSystem` 구체 클래스를 직접 쓰고(FinishTargetScanner.cs:58,60), 인터페이스인 `IFinishTargetProvider`조차 `IReadOnlyList<Enemy>`를 계약으로 내놓음(IFinishTargetProvider.cs:8-9).
- **해결**: `IFinishable`(스턴 걸리고 처형당할 수 있는 것) 인터페이스를 Finish 폴더에 두고, `Enemy`가 그걸 구현하게 뒤집음.

### 7-2. 한 번 처형할 때 주변 검사를 세 번 반복함

- **문제**: 적이 많은 곳에서 처형을 쓰면 순간적으로 프레임이 떨어짐.
- **원인**: `CanFinish`, `GatherStunTargets`, `GatherExecuteTargets`가 **각자 `ScanTargets`를 다시 부름**(FinishTargetScanner.cs:25,32,38). 한 처형 동작에 반경 20m 물리 검사가 3번 돎.
- **해결**: 같은 프레임이면 이전 결과를 재사용함(프레임 번호를 기억해 두고 비교).

### 7-3. 적이 32명을 넘으면 뒤쪽이 조용히 무시됨

- **문제**: 적이 많이 모인 구간에서 일부 적만 처형되고 나머지는 멀쩡함.
- **원인**: 검사 결과 버퍼가 32칸 고정이고, 넘치면 잘림(FinishTargetScanner.cs:15).
- **해결**: 결과 수가 버퍼 크기와 같으면 "잘렸을 수 있음"을 경고하거나 버퍼를 늘림.

## 8. Health

### 8-1. 새 게임을 시작해도 지난 판 체력이 따라옴

- **문제**: 죽고 새로 시작했는데 체력이 만피가 아니라 죽기 직전 체력으로 시작함.
- **원인**: 씬 전환에 체력을 넘기려고 `static` 변수에 저장해 두는데(PlayerHealth.cs:22), 이걸 비워 주는 "새 게임 시작" 지점이 코드에 없음.
- **해결**: 새 게임 시작 로직에서 `_carriedCurrent`를 비움. 이미 코드에 `ponytail:` 주석으로 예고돼 있는 부채임.

### 8-2. 체력의 주인인데 죽었는지는 남이 판단함

- **문제**: 사망 조건(예: 1 이하면 사망)을 바꾸려는데 어디를 고쳐야 할지 헷갈림.
- **원인**: `PlayerHealth`는 숫자만 관리하고, "0 이하면 죽음"이라는 판단은 `PlayerDamageReceiver.cs:67`에 있음.
- **해결**: `IHealthInfo`에 `IsAlive`를 두고 사망 판정을 체력 시스템 안으로 가져옴.

### 8-3. 아무도 안 쓰는 public 메서드

- **문제**: 없음(당장 고장은 안 남). 다만 읽는 사람이 "누가 부르지?" 하고 시간을 씀.
- **원인**: `Setup(float)`이 public인데 외부 호출이 0곳임. 자기 `Awake`에서만 부름(PlayerHealth.cs:41).
- **해결**: `private`으로 내림. 필요해지면 그때 올리면 됨.

## 9. Hitbox

### 9-1. 짧은 공격 판정이 통째로 빠질 수 있음

- **문제**: 분명 맞는 타이밍인데 가끔 아무것도 안 맞음. 재현이 잘 안 되는 유령 버그가 됨.
- **원인**: 히트박스를 켜는 건 `Update`(애니 진행률 기준)인데, 실제 겹침 검사는 `FixedUpdate`에서 함(PlayerHitboxHandler.cs:70). 지속시간이 물리 스텝(기본 0.02초)보다 짧으면 검사 한 번을 못 받고 사라짐.
- **해결**: 활성화된 히트박스는 **최소 한 번은 검사**하도록 보장함(등록 즉시 1회 검사 또는 최소 지속 프레임 보장).

### 9-2. 타격 채널이 Hitbox 폴더 안에 있는데 사실상 게임 공용임

- **문제**: 플레이어 히트박스를 갈아 끼우려는데, CameraSystem·CombatSystem 4개 클래스가 이 폴더의 `HitChannel`을 쓰고 있어 같이 끌려옴.
- **원인**: `HitChannel`·`HitReport`가 PlayerSystem/Hitbox 안에 정의돼 있는데, 구독자는 `PlayerCameraShake`, `HitEffectHandler`, `HitFlashHandler`, `HitStopHandler`로 전부 바깥임.

## 10. Movement

### 10-1. 카메라가 바뀌면 조작 방향이 틀어짐

### 10-2. 히트스탑 감지를 "애니 속도 0"이라는 부작용으로 함

- **문제**: 다른 이유로 애니 속도를 0으로 만들면(디버그, 컷신 등) 이동이 통째로 멈춤.

### 10-3. 이 시스템 하나가 플레이어 전체의 허브가 됨

- **문제**: Movement를 갈아 끼우려면 입력·상태·스왑·락온·캐릭터 5개 시스템을 다 이해해야 함.

- **해결**: 속도 소스가 필요한 건 "이동해도 되나 / 회전해도 되나" 같은 **작은 질문 한 개**임. 시스템 전체가 아니라 그 질문만 담은 작은 인터페이스를 넘김.

### 10-4. 발밑 감지기가 없으면 경사에서 안 미끄러지는데 표시가 없음

- **문제**: 급경사에 올라가도 미끄러지지 않고 서 있음. 왜 그런지 알 방법이 없음.

- **해결**: 없으면 `Debug.LogError`로 알림.

### 10-5. 적 레이어 이름이 코드에 박혀 있음

- **문제**: 레이어 이름을 바꾸면 스킬 이동 중 적 관통 방지가 조용히 꺼짐.
- **원인**: `LayerMask.GetMask("Enemy")`를 `static readonly`로 하드코딩(SkillVelocitySource.cs:15). 이미 `ponytail:` 주석으로 예고돼 있음.
- **해결**: 인스펙터의 `LayerMask` 필드로 빼서 Mover가 생성자로 넘김.

## 12. States

### 12-1. 상태 이름과 애니메이션 이름이 문자열로 몰래 묶여 있음

### 12-2. 상태를 하나 늘리면 거대한 switch를 손봐야 함

- **문제**: 새 스킬 상태를 추가했는데 아무리 입력해도 전환이 안 됨. 규칙을 빠뜨린 것.
- **원인**: 전환 규칙 전체가 `TryGetNextState`의 하드코딩 switch에 들어 있음(PlayerStateMachine.cs:82-106).
- **해결**: 의도된 설계라면 그대로 두되, **"상태 추가 시 여기도 고친다"를 문서에 명시**함. 지금은 코드를 읽어야만 알 수 있음.

### 12-3. 입력 게이트가 사실은 규칙 허브임

- **문제**: 입력 처리 방식만 바꾸려 해도 스왑·락온·처형 시스템을 다 알아야 함.
- **원인**: `PlayerStateInputGate`가 7개 시스템을 주입받고, "NormalAttack3에서 기본공격을 누르면 스왑 후 특수공격" 같은 **게임 규칙**까지 직접 판단함(PlayerStateInputGate.cs:81-93).
- **해결**: 게이트는 "입력을 트리거로 바꿔 보내기"만 하고, 조건부 규칙은 상태 머신 쪽으로 옮김.

### 12-4. 등록된 상태가 하나도 없으면 시작하자마자 예외

- **문제**: 프리팹에서 StateData 목록을 비워 두면 게임 시작과 동시에 예외가 남.
- **원인**: `_states.Values.First()`가 비어 있으면 예외를 던짐(PlayerStateMachine.cs:122).
- **해결**: 비었으면 `Debug.LogError` 후 조용히 비활성화. 예외로 죽는 것보다 원인이 잘 보임.

## 15. CameraSystem

> `Assets/1.Code/Scripts/CameraSystem/` — 카메라 전환·락온·연출(셰이크·줌)·벽 투시를 담당함.

### 15-1. 카메라 주인이 둘이라 컷씬 시점이 튐

- **문제**: 컷씬에서 카메라를 원하는 각도로 맞춰 놨는데, 캐릭터를 바꾸거나 락온을 켜면 시점이 홱 돌아감.
- **원인**: 카메라를 만지는 손이 둘임. `CameraSwitcher`가 우선순위와 추적 대상을 정하는데, 컷씬 기믹 3개가 `List<CameraRole>`을 직접 주입받아 카메라 부품을 꺼내 고침(EventBossCamera.cs:21, EventCameraStop.cs:13, EventStartView.cs:14). 기믹이 바꿔 놔도 `CameraSwitcher`는 그걸 모르니 다음 알림에서 전부 덮어씀.
- **해결**: "연출이 카메라를 잠시 빌린다"는 요청 통로(`ICameraOverride` 같은)를 CameraSystem에 두고, 기믹은 그것만 주입받음. 빌려준 동안 `CameraSwitcher`는 자기 갱신을 멈춤.

### 15-2. UI가 락온 구현 클래스를 직접 씀 → 교체 불가

- **문제**: 락온 로직을 다른 클래스로 갈아 끼우면 상관없어 보이던 UI 마커가 같이 깨짐.
- **원인**: `ILockOnState`(켜졌나)와 `ILockOnTarget`(누구를 잡았나) 창구를 이미 만들어 놨는데, `LockOnMarker`가 구현 클래스 `LockOnController`를 통째로 주입받음(LockOnMarker.cs:16).
- **해결**: 주입 타입을 `ILockOnTarget`으로 바꿈. 접수창구를 만들어 놨으면 사무실로 들어가지 말아야 함.

### 15-3. "죽었다"를 레이어 번호로 짐작함

- **문제**: 멀쩡히 살아 있는 적인데 락온이 저절로 풀림. 적 프리팹 레이어를 Default(0번)로 잘못 두면 그 적은 아예 락온이 안 됨.
- **원인**: `IsDead`가 `!collider.enabled || collider.gameObject.layer == 0`으로 판정함(LockOnController.cs:122). 레이어는 물리 충돌을 나누는 값이지 생사 표시가 아님. 적 시스템에 묻지 않고 옆에서 추측하는 코드임.
- **해결**: 적 쪽이 `IsAlive`나 사망 이벤트를 내주고 그걸 물어봄. 이벤트를 쓰면 매 프레임 검사도 없어짐.

### 15-4. 부품 연결을 빠뜨려도 아무 말이 없음

- **문제**: "때렸는데 화면이 안 흔들림", "스킬 줌이 안 걸림", "락온이 안 잡힘" 제보가 오는데 콘솔에 단서가 없음.
- **원인**: 필요한 참조가 없으면 그냥 `return`함(PlayerCameraShake.cs:79, PlayerCameraZoomHandler.cs:47, LockOnTargetDetector.cs:44). "이번 상태엔 셰이크 설정이 없다"(정상)와 "임펄스 연결을 깜빡했다"(사고)가 똑같이 조용해서 사고가 정상인 척 숨음.
- **해결**: 반드시 있어야 하는 참조는 `Awake`에서 한 번 검사해 `Debug.LogError`를 냄. 매 프레임 도는 곳에서는 로그를 찍지 않음(콘솔이 도배됨).

### 15-5. 벽 투시가 플레이어 몸속 부품을 직접 꺼내 씀

- **문제**: 캐릭터 콜라이더를 `CharacterController`에서 다른 걸로 바꾸면 투시 구멍이 발밑이나 허공에 뚫림. 캐릭터만 고쳤는데 카메라가 깨짐.
- **원인**: "지금 캐릭터가 누구냐"만 창구로 받고, 그다음은 `GetComponent<CharacterController>()`로 남의 부품을 꺼내 몸 중앙을 직접 계산함(SeeThroughWall.cs:56, :95).
- **해결**: `PlayerCharacter`가 `BodyCenter`를 읽기 전용으로 내주고 그 값만 읽음. 캐릭터 교체 시 컴포넌트를 다시 찾는 캐시 코드도 통째로 사라짐.

## 16. SaveSystem

> `Assets/1.Code/Scripts/SaveSystem/` — 세이브 슬롯 저장·불러오기, 씬 복원, 저장 파일 입출력을 담당함.

### 16-1. 세이브 데이터를 담는 그릇이 UI 폴더에 있음 → 교체 불가

- **문제**: 불러오기 창 UI를 갈아 끼우거나 `UISystem/MenuFunction` 폴더를 정리하면 세이브 기능 전체가 컴파일 에러로 멈춤.
- **원인**: 슬롯 목록 타입 `SaveSlotInfo`와 창구 `ISaveSlots`가 UI 폴더에 정의돼 있는데(UISystem/MenuFunction/ISaveSlots.cs:4, :13), 그걸 만들어 주는 쪽은 SaveSystem임(SaveSlotManager.cs:43, SlotLoadRunner.cs:9). 화살표가 `UI → 세이브` 한 방향이어야 하는데 서로를 가리킴.
- **해결**: 두 타입을 `.cs.meta`와 함께 SaveSystem 폴더로 옮김. UI는 지금처럼 `ISaveSlots`만 주입받으면 되므로 UI 코드는 안 바뀜.

### 16-2. 기믹이 세이브 구현 클래스를 통째로 주입받음 → 교체 불가

- **문제**: `SaveSlotManager`의 메서드 하나만 바꿔도 세이브와 상관없어 보이는 기믹 3개가 동시에 깨짐.
- **원인**: 인터페이스가 아니라 구현 클래스 `SaveSlotManager`·`SlotLoadRunner`를 그대로 주입받음(EventFallRespawn.cs:12-13, EventSaveGame.cs:22, EventSceneLoad.cs:26). 그래서 `DeleteAll`·`TakeSlot`까지 바깥 아무나 부를 수 있음.
- **해결**: 기믹이 실제로 쓰는 셋(저장, 지금 칸 덮어쓰기, 그 칸으로 다시 시작)만 담은 진입점 인터페이스를 SaveSystem에 두고 그것만 주입받음.

### 16-3. 세이브와 기믹이 전역 변수로 서로를 부름

- **문제**: 씬을 넘어갈 때 체력·캐릭터가 이상하게 복원되면 볼 곳이 두 시스템에 흩어져 있음. 기믹 쪽 `EventSceneLoad`를 지우면 SaveSystem이 컴파일 안 됨.
- **원인**: 기믹이 씬 전환 직전 값을 static에 담아 두고, 세이브 쪽 `GameStateSaver`가 새 씬 `Start`에서 직접 꺼내 감(GameStateSaver.cs:23). 게다가 이게 동작하는 근거가 "sceneLoaded가 Start보다 먼저 돈다"는 실행 순서라, 순서가 어긋나면 에러 없이 틀린 값이 들어감.
- **해결**: 씬을 넘겨 들고 갈 값의 주인을 SaveSystem 한 곳으로 정함. 기믹은 넣기만 하고, 꺼내 쓰는 것도 SaveSystem 안에서 끝냄.

### 16-4. 저장이 실패해도 아무도 모름

- **문제**: 디스크가 꽉 찼거나 권한이 막혀 저장이 실패해도 게임은 그대로 진행됨. 플레이어는 저장된 줄 알고 껐다가 진행이 통째로 날아감.
- **원인**: 파일 쓰기 `catch` 블록이 비어 있어 로그가 없음(LocalSaveFileHandler.cs:37-45). 그 `false`를 받는 쪽도 확인하지 않고 `_saveService?.Save(...)`로 흘려보냄(SaveSlotManager.cs:70, :102). 주입 누락과 정상 저장이 화면에서 똑같이 보임.
- **해결**: `catch (Exception e)`로 받아 경로와 예외를 `Debug.LogError`로 남기고, `Save`의 반환값을 확인함. 데이터가 사라지는 실패는 조용하면 안 됨.

### 16-5. 저장 파일 이름을 문자열 리플렉션으로 찾음

- **문제**: 새 저장 데이터 클래스에서 상수 이름을 `FileName`이 아니게 적거나 `public`을 빼먹으면, 저장은 성공한 척하면서 엉뚱한 파일에 쌓이고 불러오기만 빈 값을 줌.
- **원인**: `typeof(T).GetField("FileName")`으로 이름을 문자열로 찾고, 못 찾으면 클래스 이름으로 대체하고 넘어감(SaveManager.cs:84-94). 문자열이라 컴파일러가 검사해 주지 못함.
- **해결**: `ISaveData`에 `string FileName { get; }`을 두고 각 데이터 클래스가 구현하게 함. 빠뜨리면 실행 중이 아니라 컴파일 시점에 잡히고, 리플렉션도 사라짐.

### 16-6. 구현이 하나뿐인 인터페이스

- **문제**: 당장 깨지는 건 없음. 저장 코드를 따라갈 때 한 단계를 더 거치게 됨.
- **원인**: `ISaveFileHandler`의 구현이 `LocalSaveFileHandler` 하나뿐임(ISaveFileHandler.cs:3). 클라우드·암호화 저장을 미리 대비한 자리인데 지금 그게 없음.
- **해결**: 급하지 않음. 16-1~16-5를 정리한 뒤, 클라우드 저장 계획이 없으면 인터페이스를 지우고 `SaveManager`가 직접 씀.

### 16-7. 컨벤션에서 벗어난 저장 필드 (수정 보류)

- **문제**: `KeyBindingEntry.actionName`·`keyCode`, `SerializableVector3.x`·`y`·`z`가 PascalCase 규칙에서 벗어나 있음.
- **원인**: `JsonUtility`가 필드명을 그대로 json 키로 쓰기 때문에, 이름을 고치면 이미 저장된 키 설정과 플레이어 위치를 못 읽음.
- **해결**: 고치지 않기로 함. 이유를 각 파일 주석으로 남겨 뒀음(KeyBindingEntry.cs:8, SerializableVector3.cs:9).

## 17. UISystem

> `Assets/1.Code/Scripts/UISystem/` — 메뉴 창 열고 닫기, 설정·저장슬롯 화면, 체력 HUD, 클릭음 같은 UI 연출을 담당함.

### 17-1. 같은 이름표를 두 창에 붙이면 한 창이 조용히 사라짐

- **문제**: 새로 만든 창이 아무리 눌러도 안 열림. 대신 엉뚱한 옛날 창이 열림. 콘솔은 깨끗함.
- **원인**: `UIRoot`가 자식 창을 `_registry[window.Id] = window`로 등록함(UIRoot.cs:86). 사전(Dictionary)은 같은 열쇠에 값을 또 넣으면 **덮어씀**. 그래서 `WindowType`을 같은 값으로 둔 창이 둘이면 뒤에 등록된 하나만 살아남고 앞의 것은 흔적 없이 사라짐.
- **해결**: 등록할 때 이미 그 이름표가 있으면 `Debug.LogError`로 두 오브젝트 이름을 같이 찍음. 사람이 인스펙터에서 실수한 걸 사람이 볼 수 있게 만드는 게 목적임.

### 17-2. 저장 슬롯을 불러오는 길이 두 갈래로 나 있음

- **문제**: 불러오기 동작을 고쳐야 할 때 한쪽만 고치고 끝냄. 그러면 어떤 버튼은 새 동작, 어떤 버튼은 옛 동작으로 갈림.
- **원인**: 완전히 같은 일(`_saveSlots.LoadSlot(_slotList.SelectedIndex)`)을 하는 코드가 두 군데 있음. `LoadConfirmWindow.cs:15`와 `LoadSlotButton.cs:29`. 심지어 슬롯 목록을 받는 방법도 달라서, 하나는 인스펙터 연결(LoadConfirmWindow.cs:9), 하나는 `[Inject]`(LoadSlotButton.cs:13)임.
- **해결**: `LoadConfirmWindow` 하나만 남기고 `LoadSlotButton`을 지움. 확인창이 이미 "예를 누르면 불러온다"를 담당하므로 버튼 쪽은 할 일이 없음.

### 17-3. 연결이 빠져도 버튼이 그냥 아무 반응 없음

- **문제**: "불러오기를 눌렀는데 아무 일도 안 남", "슬라이더를 움직여도 소리가 안 변함" 제보가 오는데 콘솔에 단서가 하나도 없음.
- **원인**: 주입이 실패했을 때 조용히 넘어가는 코드가 여러 곳임. `_saveSlots?.LoadSlot(...)`(LoadConfirmWindow.cs:15)의 `?`는 "없으면 그냥 아무것도 안 함"이라는 뜻이고, `if (_saveSlots == null) return;`(SlotListWindow.cs:45), `if (_mouseSettings == null) return;`(MouseSpeedSlider.cs), `if (_soundSettings == null) return;`(VolumeSlider.cs)도 전부 같음.
- **해결**: 이 값들은 **없으면 안 되는 것**이므로 `Start`에서 한 번 검사해 `Debug.LogError`를 냄. "설정이 없어서 안 하는 것"(정상)과 "연결을 깜빡한 것"(사고)이 지금은 화면에서 똑같이 보임.

### 17-4. 클릭음 컴포넌트가 씬에 둘이면 소리가 두 번 남

- **문제**: 버튼 하나를 눌렀는데 딸깍 소리가 겹쳐서 두 번 남. 볼륨이 두 배로 느껴짐.
- **원인**: `ButtonClickSound`가 시작할 때 씬의 **모든 버튼에** 소리 재생을 붙임(ButtonClickSound.cs:19-27). 이 컴포넌트가 씬에 둘 있으면 버튼마다 두 번 붙음. "하나만 놓으라"는 규칙이 주석에만 있고 코드는 검사하지 않음.
- **해결**: `Awake`에서 씬에 자기와 같은 컴포넌트가 몇 개인지 세고, 둘 이상이면 `Debug.LogError` 후 자기를 꺼버림.

### 17-5. UI가 락온 구현 클래스를 직접 씀 → 교체 불가

- **문제**: 락온 로직을 다른 클래스로 갈아 끼우면 상관없어 보이던 UI 마커가 같이 깨짐.
- **원인**: `LockOnMarker`가 창구(`ILockOnTarget`, `ILockOnState`)를 두고도 구현 클래스 `LockOnController`를 통째로 주입받음(LockOnMarker.cs:16).
- **해결**: 15-2와 같은 건임. 주입 타입을 인터페이스로 바꾸면 양쪽이 한 번에 해결됨.

### 17-6. 창을 여는 버튼이 다른 창 클래스를 직접 알고 있음

- **문제**: 슬롯 목록 창을 다른 방식으로 다시 만들면, 관련 없어 보이던 확인창과 버튼이 같이 컴파일 에러가 남.
- **원인**: `LoadConfirmWindow`와 `LoadSlotButton`이 구체 클래스 `SlotListWindow`를 직접 참조해 `SelectedIndex`를 읽어감(LoadConfirmWindow.cs:9, LoadSlotButton.cs:13). "지금 고른 슬롯 번호"라는 값 하나 때문에 창 클래스 전체를 알아야 하는 상태임.
- **해결**: 고른 슬롯 번호의 주인을 `UIRoot`나 별도의 작은 보관소로 옮기고, 창끼리는 서로를 모르게 함.

### 17-7. 다른 시스템의 enum을 그대로 씀 → 교체 불가

- **문제**: 소리·상태·입력·캐릭터 시스템 중 하나만 정리해도 UI가 같이 컴파일 에러가 남.
- **원인**: 남의 폴더에 정의된 값 목록을 UI 코드에 그대로 적어 씀. `SoundType`(ButtonClickSound.cs:34), `PlayerStateType`(UIFader.cs:51), `PlayerCharacterType`(CharacterButtonGraphic.cs:38), `InputActionType`(KeyRebindButton.cs:24, UIRoot.cs:93), `VolumeCategory`(VolumeSlider.cs:11), `GameStateType`(UIRoot.cs:58).
- **해결**: 전부 끊는 건 비현실적임. 대신 **"UI는 다른 시스템의 enum을 인스펙터 선택지로만 쓴다"**를 규칙으로 못 박고, enum을 보고 UI가 직접 분기·판단하는 코드(UIFader.cs:51 같은)만 인터페이스 뒤로 숨김.

### 17-8. 키 재설정 로직이 통째로 버튼 안에 들어 있음

- **문제**: 키 설정을 코드에서 초기화하거나 프리셋으로 되돌리는 기능을 넣으려면, 버튼 컴포넌트를 뜯어야 함. 버튼 없이는 키를 못 바꿈.
- **원인**: `KeyRebindButton`이 InputSystem 에셋을 직접 받아 `PerformInteractiveRebinding`으로 키를 바꾸고 저장까지 함(KeyRebindButton.cs:46-82). UI 버튼인데 실제로는 입력 시스템의 일을 함.
- **해결**: "이 액션의 이 방향 키를 다시 받아라"를 InputSystem 쪽 창구(`IKeyRebinder` 같은)로 옮기고, 버튼은 그걸 호출하고 결과 글자만 표시함.

## 전체 요약

가장 많이 반복된 문제는 두 가지임.

1. **조용한 실패** — 잘못된 상황에서 로그 없이 그냥 넘어가는 코드가 15개 시스템 중 10곳에 있음. 게임은 안 죽지만 원인을 못 찾음.
2. **시스템끼리 클래스 이름으로 직접 묶임** — 폴더를 독립 시스템으로 보면, 지금 상태에서 **혼자 떼어낼 수 있는 시스템은 사실상 없음**. 특히 `PlayerCharacter`(Character)와 `StateEventCategory`·`IStartData`(States/Data)가 거의 모든 폴더에 박혀 있음. CameraSystem도 같은 이유로 UI·기믹과 묶여 있음.

먼저 손댈 순서로는 1번(조용한 실패)이 쉬움. 로그 한 줄씩만 추가하면 되고, 그것만으로도 앞으로의 디버깅 시간이 크게 줄어듦.
