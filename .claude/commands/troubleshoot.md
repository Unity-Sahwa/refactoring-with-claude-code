# 목적
- 문제를 바로 고치지 않는다. **원인을 확정한 뒤에** 해결 방법을 제시한다.
- 섹션 1(원인 분석)이 끝나기 전에 섹션 2(해결 방법)로 넘어가지 않는다.
- 추측과 근거를 섞지 않는다. 사용자 편을 들지 않는다.

---
 
# 섹션 1. 문제 원인 분석

## 1-1. 되묻기 (필수)
사용자의 문제 설명은 대부분 두루뭉실하다. 코드를 읽기 전에 **모르는 것부터 묻는다.**

- 증상: 정확히 무엇이 어떻게 되는가. (에러 메시지 원문, 로그, 화면, 수치)
- 재현: 언제 발생하는가. 항상인가 가끔인가. 재현 절차는.
- 범위: 특정 상황·기기·빌드에서만인가.
- 변경점: 언제부터 그랬는가. 직전에 무엇을 바꿨는가.
- 이미 시도한 것: 무엇을 해봤고 결과는 어땠는가.

**규칙**
- 이미 답이 나온 항목은 묻지 않는다. 모르는 항목만 묻는다.
- 답 없이 진행하면 결론이 틀어질 항목은 **답을 받기 전까지 멈춘다.**
- 답 없이도 확인 가능한 것(코드 읽기, 로그 확인)은 먼저 확인한 뒤 묻는다.

## 1-2. 1차 원인 가설
- 들은 내용과 코드만으로 원인 후보를 제시한다. 가능성이 높은 순으로.
- 각 후보마다 **근거 한 줄**(어느 코드 / 어느 증상 때문인지)을 적는다.
- 이 시점의 내용은 **검증 전 가설**임을 명시한다.

## 1-3. 웹 근거 대조 (필수)
`evidence-research` 커맨드의 규칙을 그대로 적용해 조사한다.
(출처 URL + 원문 그대로 인용 + 교차검증 표기 + 상충 근거 양쪽 제시)

- 조사 대상: 공식 문서/이슈 트래커 → 기술 표준 → 커뮤니티(포럼, Q&A) → 블로그·댓글 순.
- 커뮤니티 글·댓글도 유효한 근거로 취급하되, **공식 문서와 신뢰도를 구분해 표기**한다.
- 근거를 못 찾으면 멈추고 사용자에게 알린다. 빈손을 추측으로 채우지 않는다.

찾은 근거는 1-2의 가설과 대조해 **각각 아래로 판정**한다.

| 판정 | 의미 |
|---|---|
| **지지** | 1차 가설과 같은 방향 |
| **충돌** | 1차 가설을 부정 |
| **다른 방향** | 가설에 없던 제3의 원인을 가리킴 |
| **무관** | 증상은 비슷하나 조건이 다름 |

## 1-4. 2차 원인 (재제시)
- 1-3 결과를 반영해 원인을 다시 제시한다. **확정 / 수정 / 미확정** 중 하나로 명시한다.
- 1차 가설이 틀렸으면 **틀렸다고 그대로 적는다.** 말을 맞추지 않는다.
- 미확정이면 남은 후보와, 무엇을 더 알아야 좁힐 수 있는지 적는다.

## 1-5. 원인 검증 테스트 (필수)
사용자가 직접 원인을 눈으로 확인할 수 있게 만든다.

- **재현 조건:** 무엇을 하면 문제가 나타나는가.
- **확인 방법:** 로그 출력, 값 확인, 설정 토글, 최소 재현 코드 등 구체적 절차.
- **예상 결과 대조표:** 원인이 맞다면 무엇이 보이고, 아니라면 무엇이 보이는가.
- 원인을 **가르는** 테스트여야 한다. 맞든 틀리든 같은 결과가 나오는 테스트는 쓰지 않는다.
- 사용자 확인 결과를 받기 전까지 섹션 2로 넘어가지 않는다.

# 섹션 2. 해결 방법 제시

**전제:** 1-5에서 원인이 확인된 뒤에만 작성한다.

## 2-1. 방법 목록
방법을 2개 이상 제시하고, 각각 아래를 적는다.

- **방식:** 무엇을 어떻게 바꾸는가.
- **원인 대응:** 근본 원인을 없애는가, 증상만 막는가. (명시할 것)
- **영향 범위:** 어떤 파일·시스템이 함께 바뀌는가.
- **새로 생길 문제:** 이 방법이 부를 부작용·제약·성능 비용. **없으면 "없음"이라고 적되, 억지로 없다고 하지 않는다.**
- **되돌리기:** 실패 시 원복이 쉬운가.

## 2-2. 비교표
| 방법 | 원인 대응 | 작업량 | 부작용 | 되돌리기 |
|---|---|---|---|---|

## 2-3. 추천과 선택
- 추천안 하나와 그 이유를 적는다. 사용자가 원하는 답이 아니어도 근거대로 적는다.
- 최종 선택은 사용자가 한다. **선택을 받기 전에 코드를 수정하지 않는다.**
