# 필수 규칙
- 아래 순서에 맞게 작업을 수행한다.
- 순서에 예외는 존재하지 않는다.
- 생략하거나 임의로 순서를 조정하지 않는다.

# 1. 변경사항 확인

- `git status`와 `git diff HEAD`로 staged·unstaged·untracked 파일을 모두 확인한다.
- 변경사항이 없으면 "분류할 변경사항이 없습니다."를 출력하고 종료한다.

# 2. 변경사항 세부 분류
- Commit 그룹 분류 전에 각 변경사항을 아래 단위로 파악한다. 번호는 부여하지 않는다.
- 무엇을, 왜 변경했는지 자세하게 알기 위해 분류.

## 변경 위치

### 코드 파일 변경 위치
- 클래스 내의 interface 또는 abstract 관련 변경사항은 묶어서 분류.
- 클래스의 변수 변경사항은 묶어서 분류.
- 로컬 메서드 변경사항은 각 메서드마다 분류
- 코드 파일 외의 파일들은 파일 단위로 분류

### 그 외 변경 위치
- 코드 파일을 제외하고는 변경 위치는 필요가 없다.

### 예시
예: `PlayerMovement.cs`에 아래 변경이 있을 때

변경 내용:
- `_speed`, `_jumpForce` 클래스가 가지는 변수 추가
- `IMovable` 인터페이스 구현 추가
    - `float ForceMount` 인터페이스 프로퍼티 추가
    - `SubMove()` 인터페이스 메서드 추가
- `BaseMovement` 상속(abstract) 추가
    - `float baseSpeed` 상속 변수 추가
    - `BaseMove()` 상속 메서드 추가
- `Move()` 메서드 수정
- `Jump()` 메서드 추가

분류 결과:

| 변경 위치 | 분류 요소 |
|---|---|
| 변수 그룹 | `_speed`, `_jumpForce` |
| IMovable | `ForceMount`, `SubMove()` |
| BaseMovement |  `baseSpeed`, `BaseMove()` |
| PlayerMovement.Move | `Move()` |
| PlayerMovement.Jump | `Jump()` |

## 무엇을, 왜 작성 
- 아래 형식으로 각 분류 항목마다 작성한다.
  - `[무엇을]` : [왜]

- 근거가 구체적으로 확실하다면 [왜] 를 작성한다.
- 근거가 추상적이거나 판단이 필요하다면 [왜]에다가 '?' 만 작성한다.
- 근거가 필요없다면 [왜] 에다가 '-' 만 작성한다
- 변경사항에서 무슨 활동을 하였는지 [무엇을] 을 작성한다.
- [무엇을] 은 독립적인 책임 단위로 나눠서 작성한다. 1개의 변경위치에 N개의 [무엇을]이 존재할 수 있음.
- 무엇을 했는지, 왜 했는지가 같다면 통합해서 작성한다.

PlayerMovement.cs 예:
  변수 그룹
    `_speed 추가` : 이동 속도를 외부에서 조정하기 위해
    `_jumpForce 추가` : ?
  PlayerMovement.Move
    `이동 로직 분리` : 단일 책임 원칙 적용
  IMovable
    `ForceMount 프로퍼티 추가` : ?

- 이 내용이 5단계 파일 형식의 <details> 안 내용과 1:1 대응된다.


## 변경 타입
- feat: 기능 및 설계의 추가/구현
- fix: 버그 수정
<!--refactor: (`Assets\1. Code\Scripts` 내의 코드 한정) 기존 구현을 보완 및 개선하는 것-->
- test: 테스트 목적으로 작성된 것들. 보통 메서드, 또는 클래스명으로 'test'가 포함되어 있음.
- perf: 성능 개선
- docs: 문서 생성 / 수정
- file: 파일 추가/삭제/이름 변경
- chore: 코드 동작에 관련 없는 기타 변경

# 3. 변경사항 그룹화
- 2 단계에서 파악한 변경사항을 아래 기준에 따라 그룹화한다.
- 아래 번호 순서가 곧 적용 우선순위다. 번호가 낮을수록 먼저 적용된다.
- 하나의 그룹이 한 번의 commit 이다.

1. 삭제된 폴더/파일은 무조건 `file` 변경타입 그룹에 포함시킨다.
2. 내용 수정 없이 발생한 변경(이름 변경·경로 이동)도 `file` 그룹에 포함시킨다.
   - 이동과 내용 수정이 동시에 발생한 경우, 아래 규칙(3~5)을 따른다.
   - 같은 이름의 폴더/파일이 삭제되고 생성된 경우 이동으로 판단한다
3. `Assets/1.Code` 하위 변경사항은 폴더(System 단위)별로 1차 그룹화한다.
4. Claude 관련 변경사항(`.claude/`, `CLAUDE.md`)은 1차 그룹화한다.
5. 그 외 변경사항은 변경 타입이 같은 것끼리 그룹화한다.
6. 3·4단계 그룹 내부에서 변경 타입이 다르면 타입별로 분리한다.


# 4. 변경사항 리스트 작성
- 그룹 순서대로 번호를 부여한다. 번호는 전체에서 연속된다.

## 예시
그룹 1에 3개, 그룹 2에 2개일 때, 추가로 여러 그룹이 있으 때:
그룹 1 -> 1,2,3
그룹 2 -> 4,5
...
그룹 x -> n-1, n


# 5. 파일 생성 및 작성
- 파일을 생성하고 내용을 작성한다.


## 파일 정보
- 경로: `.claude\git\diff\`
- 파일명: `diff_년월일시간` (예: `diff_202605292039`) 
  - 한국서울 기준으로 현재시간을 작성하긴

## 파일 형식

```
## 변경사항 리스트
<fieldset>

| 번호 | 폴더/파일명 | 변경 위치 | 변경 타입 |
|---|---|---|---|
| 1 |  |  |  |
| 2 |  |  |  |
| 3 |  |  |  |
| 4 |  |  |  |

<details>
<summary>[1] 요약</summary>

`무엇을` : 왜 <br>

</details>

<details>
<summary>[2] 요약</summary>

`무엇을1` : 왜1 <br>
`무엇을2` : 왜2 <br>

</details>

<details>
<summary>[3,4] 요약</summary>

`무엇을1` : 왜1 <br>
`무엇을2` : 왜2 <br>
`무엇을3` : 왜3 <br>

</details>
</fieldset><br>

(그룹수만큼 반복)...
```


## 작성 규칙
- 하나의 `<fieldset>` = 하나의 Commit 그룹
- `<fieldset>` 안에 해당 그룹의 번호 표, `<details>` 토글을 순서대로 작성한다.
- `</fieldset>` 뒤에 `<br>` 추가
- `<details>` 형식:
    - `<summary>` : `[번호] 요약`
    - `</summary>` 다음 반드시 빈 줄 추가
    - 내용 형식: `` `무엇을` : 왜 ``
    - 항목이 여러 개면 줄 끝에 `<br>` 추가
    - `왜`: 근거가 명확한 추론만 작성. 근거가 필요없는 경구에는 공백, 근거가 명확하지 않는 경우에는 `?`만 표기

- 표의 각 행은 파일/폴더 1개에 대응한다. 여러 항목을 1행에 합치거나 `/`로 이어붙이는 것은 금지한다.
- 항목 통합은 <details>의 [1,2,3] 묶음 표기로만 한다.
- `폴더/파일명`에는 이름과 타입만 작성한다. (경로 작성을 금지한다.)

# 6. 피드백 반영
- 파일 작성 완료 후 "피드백을 기다리겠습니다."를 출력하고 대기한다. (다른 말은 하지 않는다)
- 사용자가 파일 내 `<!---->` 주석으로 피드백을 작성한다.
- 사용자가 업데이트 지시를 하면 파일을 읽어 주석을 확인하고 수정한다.
- 수정 완료 후 `# 6. 피드백 반영` 단계를 반복한다.

# 금지 항목
- `git add` / `git commit` / `git reset` 등 이력 변경 명령 실행
- 사용자 확인 없이 다른 Skill, Agent 자동 호출
- 변경사항에 없는 내용을 지어내거나 추측하여 작성
