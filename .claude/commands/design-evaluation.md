# 시스템 설계 평가 규칙 (System Design Evaluation Convention)

설계를 **"좋은 설계"** 와 **"객체지향"** 두 축으로 평가한다.
표를 채우는 과정 자체가 평가다 — 표 **위 "먼저 질문"**, 표 **아래 "출력 형식"** 만 함께 본다.

---

## 1. 평가 전 — 먼저 질문 (질문표)

평가를 시작하기 전에 아래를 사용자에게 묻는다. **답이 정해져야** "단순한가 / 과설계인가", "이 결합이 문제인가 / 허용되나"를 가를 수 있다.

| 묻는 것 | 질문 |
|---------|------|
| 범위 | 시스템에 해당하는 파일은 무엇인가? |
| 책임 경계 | 이 시스템은 무엇까지 하고, 무엇은 안 하나? |
| 변화 방향 | 앞으로 자주 바뀔 부분은 어디인가? |
| 성능 | 매 프레임 도나? 한 번에 많이 만들어지나? |
| 재사용 | 이 시스템만 쓰나, 다른 데서도 쓰나? |
| 확장 계획 | 지금 확정된 확장이 있나, 아니면 나중 일인가? |
| 규모 | 동시에 몇 개나 움직이나? (수십 개 ↔ 수만 개) |
| 공유 로직 | 여러 종류가 같은 로직을 함께 쓰나? (예: 몬스터 공통 → 고블린·스켈레톤) |
| 꼭 필요한가 | 이 패턴, 정말 필요해서 쓰나? (멋이 아니라 필요로) |

---

## 2. 평가 축 1 — 좋은 설계인가

| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 단순함 | 지금 요구에 비해 과한 구조가 없나 | 지금 필요한 만큼만 만듦 | 안 쓰는 유연성을 미리 넣음 | 안 올 확장까지 미리 구현(과설계), 패턴을 억지로 끼움 |
| 예상 변화 대응 | 올 만한 변화에 기존 코드를 얼마나 고치나 | 새 기능 추가 시 기존 코드 거의 안 건드림 | 작은 변화에도 여러 곳을 함께 고침 | 변화 방향을 안 정하고 "전부 다 열어둠" |
| 낮은 결합 | 한 곳을 바꿀 때 파급이 적나 | 한 곳 수정이 그 안에서 끝남 | 한 곳 바꾸면 연쇄로 깨짐 | 구체 클래스를 직접 호출, 전역·싱글톤 참조 |
| 책임 분리 | 한 덩어리가 한 가지 일만 하나 | 역할이 명확히 나뉨 | 한 덩어리가 여러 일을 떠안음 | 매니저가 규칙·생성·상태까지 다 떠안는 God 클래스 |
| 테스트 용이성 | 주변을 가짜로 갈아끼워 따로 테스트되나 | 의존성을 주입받아 격리 가능 | 내부에서 직접 만들어 격리 불가 | 내부에서 `new`, 싱글톤, 실제 Animator/엔진 직접 호출 |
| 디버깅 용이성 | 문제 생겼을 때 흐름 추적이 쉽나 | 데이터·호출 흐름이 명확 | 추적이 어려움 | 숨은 의존·전역 상태, 트리거가 여러 곳에 흩어짐 |

## 3. 평가 축 2 — 객체지향인가

| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 캡슐화 | 내부 상태를 숨기고 정해진 통로로만 다루나 | 상태는 감추고 메서드로만 접근 | 내부 값을 밖에서 직접 만지게 열어둠 | Inspector로 직접 변수 받기(`[SerializeField]`/`public`), `protected` 날 필드 직접 대입 |
| 책임 분리 | 한 **객체**가 한 가지 책임만 지나 | 객체별 책임이 분명 | 한 객체가 모든 걸 처리 | 입력·전환·연출을 객체 하나가 다 앎 |
| 느슨한 결합 | 객체끼리 약속(인터페이스)으로 연결되나 | 인터페이스/추상으로 간접 연결 | 구체 클래스끼리 직접 호출 | 클래스 직접 결합, 구체 enum 값에 직접 의존 |
| 다형성 활용 | 같은 약속을 여러 구현이 다르게 채우나 | 부르는 쪽은 누가 하든 똑같이 호출 | 종류마다 if/switch 분기 | 전환·행동 규칙을 if-else 떡칠로 처리 |
| 의존성 주입 | 필요한 것을 밖에서 받아오나 | 주입으로 받음 | 내부에서 직접 생성·검색 | `Activator.CreateInstance`·`Find`로 직접 조달, 싱글톤 자기 노출 |

> 축1과 축2의 "책임 분리"는 다르다 — **축1은 시스템/덩어리 단위**, **축2는 객체 단위**다.

---

## 4. 평가 축 3 — 개인 평가표 (계속 추가)

| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 씬 전환 안전성 | 씬이 바뀔 때 잔존·누수·에러 없이 정리되나 | 켜져 있던 것들이 깔끔히 정리되고 참조가 끊기지 않음 | 씬 넘으면 객체가 남거나 참조가 끊겨 null로 터짐 | DontDestroyOnLoad로 살린 객체가 씬별 객체를 참조(dangling), 풀·핸들 미해제로 누수 |
| 한 줄 흐름 설명 | 시스템 전체 흐름을 한 문장으로 말할 수 있나 | 단계가 화살표 한 줄로 이어짐 (예: Rent→부착→Setup→켜기→수명→Return) | 흐름이 갈래쳐 한 줄로 안 됨 | 책임이 흩어져 설명에 "그리고/또"가 계속 붙음 |

---

## 5. 평가 결과 — 이렇게 쓴다

- 두 축(좋은 설계 / 객체지향) **각각** 기준별 충족·미흡을 표로 정리하고 근거를 단다.
- **문제·단점을 장점보다 더 많이, 더 구체적으로** 쓴다 — 어디가 왜 위험하고 언제 터지는지까지.
- **두 축을 섞지 않는다.** 좋은 설계와 객체지향은 겹치지만 다른 축이다. (객체를 써도 거대 클래스·강결합이면 나쁜 설계)
- 마지막에 **"지금 고칠 것 / 나중에 봐도 될 것"** 으로 우선순위를 제시한다.
