# 시스템 평가

> 평가 단위는 **시스템**(= `Assets/1.Code/Scripts/` 바로 아래 폴더 하나)이다.
> 클래스 단위 품질은 `code-evaluation`이 담당한다.
> 좋은 설계의 기준: **시스템 내부가 바뀌어도 외부가 신경 쓸 필요가 없는가.**

---

## 0. 절차

1. 대상 시스템 폴더의 `.cs`를 전부 읽는다. 추측하지 않는다.
2. 아래 1절 축으로 평가한다.
3. 2절 판정표를 출력한다. 판단이 갈리는 부분은 이때 사용자에게 질문한다.
4. **판정표에 `나쁨`이 하나라도 있으면 3절 초안을 만들지 않는다.**
   문제·개선 방향과 질문만 내고 멈춘다. 사용자가 코드를 고치면 1번부터 다시 돈다.
5. `나쁨`이 0개가 됐을 때만 3절 형식으로 `Docs/SystemUsageGuide.md` 항목 초안을 만든다.
6. **초안을 사용자에게 보여주고 확정을 받는다. 확정 전까지 `상태: 미확정`을 유지한다.**
7. 사용자가 확정하면 `Docs/SystemUsageGuide.md`의 해당 항목을 갱신하고 `상태: 확정`으로 바꾼다.

- 코드는 수정하지 않는다. `Docs/SystemUsageGuide.md`만 갱신한다.
- `Old/`, `_Test`, `PerformanceTest`, `Editor`는 제외한다.
- 이유: 아직 고쳐질 코드에서 뽑은 규칙은 곧 거짓이 된다. 규칙은 확정된 설계에서만 나온다.
  단, 사용자가 "남은 `나쁨`은 안 고친다"고 명시하면 그 상태를 현황으로 인정하고 초안을 낸다.

---

## 1. 평가 축

각 축은 **코드에서 눈으로 찾는 증거**로 본다. 증거가 없으면 `해당없음`으로 적는다(억지 평가 금지).

### 1-1. 경계 (외부가 내부를 얼마나 아는가)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 증거) |
|---|---|---|
| 외부가 진입점 하나만 알면 되나 | 진입점 타입 1~2개만 public | 내부 클래스가 죄다 public |
| 내부를 바꿔도 외부가 안 깨지나 | 외부는 인터페이스·채널만 참조 | 외부가 내부 구현 타입을 직접 참조 |
| 외부가 내부 상태를 직접 건드리나 | 요청·이벤트로만 소통 | 외부가 내부 필드·컴포넌트를 직접 수정 |

### 1-2. 확장 (새 종류가 늘어날 때)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 증거) |
|---|---|---|
| 새 종류 추가 시 기존 코드를 안 고치나 | 데이터(SO)·구현 추가만으로 늘어남 | 새 종류마다 기존 `switch`/`if`에 분기 덧댐 |
| 확장 지점이 하나로 모여 있나 | 추가할 자리가 분명함 | 여러 파일을 동시에 고쳐야 함 |
| 안 쓸 확장을 미리 만들지 않았나 | 지금 쓰는 만큼만 | 구현 1개뿐인 인터페이스, 호출 0곳인 훅 |

> 1-2의 마지막 줄은 앞 두 줄과 충돌한다. **지금 실제로 늘어나고 있는 종류만** 확장 대상으로 본다.
> "언젠가 늘 것 같다"는 확장이 아니라 과설계다.

### 1-3. 트러블슈팅 (터졌을 때 원인을 좁힐 수 있나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 증거) |
|---|---|---|
| 실패가 드러나나 | 잘못된 입력에 로그·예외 | 조용히 무시하고 넘어감 |
| 원인 지점이 좁혀지나 | 진입점에서 흐름이 한 갈래 | 여러 곳에서 같은 상태를 바꿈 |
| 상태를 바꾸는 주체가 하나인가 | 소유자가 분명함 | 아무나 접근해 수정 |

### 1-4. 시스템 간 연결 (다른 시스템을 제대로 썼나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 증거) |
|---|---|---|
| 참조를 규칙대로 받았나 | `Docs/SystemUsageGuide.md`의 획득 방법대로 | `[Inject]`로 받아야 할 걸 `public`·`[SerializeField]`로 끌어옴 |
| 남의 시스템 내부를 파고드나 | 진입점만 호출 | `a.b.c.d` 깊은 체이닝 |
| 외부 시스템의 enum·struct·class를 직접 쓰나 | 인터페이스만 참조 | 남의 시스템 폴더에 정의된 enum·struct·class를 이 시스템 코드에서 직접 사용 |
| 이미 있는 시스템을 재구현하지 않았나 | 기존 시스템 호출 | 같은 기능을 자기 폴더에 다시 만듦 |

## 2. 판정표 출력

1절의 모든 핵심 질문을 빠뜨리지 않고 옮긴다.

| 판정 | 축 | 핵심 질문 | 근거 (파일:줄) |
|---|---|---|---|
| 나쁨 | 1-4 | 참조를 규칙대로 받았나 | PlayerMove.cs:14 — AudioChannel을 SerializeField로 받음 |

- 판정은 `좋음` / `나쁨` / `해당없음` 셋 중 하나.
- `나쁨`에는 반드시 파일:줄 근거를 적는다. 근거 없으면 적지 않는다.

판정표 아래에는 **문제를 한 번에 하나만** 낸다. 목록으로 나열하지 않는다.
(다 보여주면 양에 질려 손을 못 댄다. 하나씩 끝내는 게 목적이다.)

한 대화에 문제 하나, **딱 2줄**로 쓴다.

```
문제 N/총개수: <실제 발생되는 또는 예상되는 문제> (파일:줄)
원인: <무엇이 무엇을 했기 때문에 발생함>
```

- 2줄을 넘기지 않는다. 코드 블록·표·배경 설명을 붙이지 않는다.
- 해결책은 적지 않는다. 사용자가 물었을 때만 낸다.
- 사용자가 "쉽게 설명해봐" 같이 **더 물었을 때만** 그 문제에 한해 자세히 푼다.
- 사용자가 승인하면 고치고, 그 다음 대화에서 다음 문제 2줄을 낸다.
- 남은 문제가 몇 개인지는 `N/총개수`로만 알린다. 내용은 미리 안 보여준다.
- `나쁨`이 아니라 판단이 필요한 질문도 같은 순번에 끼워 같은 형식으로 낸다.

## 3. Docs/SystemUsageGuide.md 항목 초안

**선행 조건: 판정표의 `나쁨`이 0개일 것.** 하나라도 남아 있으면 이 절로 넘어가지 않는다.

판정표 아래에 아래 형식으로 초안을 낸다.

이 문서를 읽는 목적은 하나다. **이 시스템이 안팎으로 어떻게 연결되는가.**
그래서 항목은 아래 세 덩어리만 쓴다. 역할·사용법·설계 규칙 같은 다른 절은 만들지 않는다.

```
## <시스템명>

- 상태: 미확정
- 역할: 한 줄

### 시스템 안쪽 (개발자용)

> 이 폴더 안의 클래스끼리 어떻게 이어지는지. 밖에서는 몰라도 되는 내용이다.

- 진입점: 외부가 이 시스템을 쓸 때 건드리는 타입
- [<쓰는 쪽> → <쓰이는 쪽>] <어떻게 받는지>. <무엇을 기준으로 무엇을 하는지>.

### 다른 시스템과의 연결 (개발자용)

> 이 시스템이 밖에서 무엇을 받아오고, 밖에 무엇을 내주는지.

- <쓰는 외부 시스템> — <무엇을 위해, 어떤 타입으로 어떻게 받는지>

### 에디터에서 쓰는 법 (비개발자용)

> 코드를 안 건드리고 씬·프리팹·SO에서 할 일.

- <씬·프리팹·SO에서 무엇을 붙이고 무엇을 채우는지 한 줄>
```

**세 절의 구분을 지킨다. 인용문 한 줄 설명도 그대로 같이 적는다.**

- **시스템 안쪽**: 이 시스템 폴더 안의 코드끼리 어떻게 이어지는지.
  진입점 타입과, 그 타입에서 실제 일을 하는 타입까지의 경로를 적는다.
- **다른 시스템과의 연결**: 이 시스템이 다른 시스템을 쓰는 지점을 전부 적는다.
  연결이 없으면 `없음`이라고 적는다. 여기 없는 시스템을 새로 끌어다 쓰면 위반이다.
- **에디터에서 쓰는 법**: 코드를 고치는 것 말고 유니티 에디터에서 할 수 있는 일을 전부 적는다.
  어떤 컴포넌트를 어디에 붙이고, 어떤 SO의 어떤 칸을 채우면 무엇이 바뀌는지.
  인스펙터에 보이는 컴포넌트·에셋 이름은 실물이므로 그대로 적는다.
  주입 문법 같은 코드 작성법만 뺀다. 바로 따라 할 수 있는 문장으로 쓴다.

**가독성 규칙**

- `##`·`###` 뒤에는 빈 줄을 하나 둔다.
- 절과 절 사이에도 빈 줄을 둔다.
- 한 항목은 한 줄이다. 두 줄이 필요하면 항목을 쪼갠다.
- 시스템 항목끼리는 `---`로 나눈다.

**주의:** 연결 설명은 코드에 안 적힌 **의도**다.
코드에서 읽어낸 것은 "지금 이렇게 쓰고 있다"는 현황일 뿐 규칙이 아니다.
그러므로 초안이라고 명시하고, 사용자 확정 전에는 절대 `상태: 확정`으로 바꾸지 않는다.
