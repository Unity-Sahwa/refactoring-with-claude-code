## 0. 수행 규칙 (반드시 지킬 것)
- `1 → 2 → 3 → 4` 순서대로 진행한다.
- 소스를 **직접 읽고** 평가한다. 추측·간소화하지 않는다.
- 주석과 코드의 정보만으로 솔직하고 기계적으로 평가한다.
- 엄격하고 진지하게, 중립적으로 판단해야 한다. 지금의 판단이 프로그램 생사여부를 판가름한다.

> 이 평가의 목적: **나 또는 누군가가 유지보수하기 좋은 설계인가.**
> 그래서 추상 원칙(SOLID 등)을 점수 항목으로 두지 않고, "유지보수가 싼가"라는 결과 4개만 본다.

## 1. 평가 전 — 먼저 질문

- `소스`(경로)가 없으면 평가를 시작하지 않는다.

| 묻는 것 | 질문 |
|---------|------|
| 소스 | 평가할 폴더/파일 경로를 넘겨라 |

## 2. 주석 확인

원칙: **"무엇"은 코드·이름이 말하게 하고, 주석은 "왜"만 적는다.** 자명하면 주석 생략.

- 각 **클래스**: 아래 2개만 필수. 나머지는 복잡할 때만.

| 질문 | O/X | 비고 |
|------|-----|------|
| `흐름` (한 줄로 단계가 이어지나) | O/X | 필수 |
| `책임/용도` (한 줄로 무슨 객체인지) | O/X | 필수 |
| `확장성`·`작동 예시` | O/X | 복잡한 시스템만 |

- 각 **메서드**: 자명하지 않을 때만 "왜". getter·한 줄·이름이 곧 설명인 메서드는 주석 없어도 O.

| 질문 | O/X |
|------|-----|
| `왜` (이 코드가 왜 이렇게/여기 있나, 함정·이유) | O/X |

- 채팅창에 확인표를 생성하고, 사용자와 피드백을 반복한 뒤 다음 단계로.

## 3. 평가

각 기준은 **코드에서 눈으로 찾는 냄새**로 본다. 냄새가 안 보이면 그 행은 `해당없음`으로 적는다(억지 평가 금지).

### 3-1. 변경 파급 (이거 하나 고치면 몇 군데가 깨지나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|-----------|------|------|
| 의존을 밖에서 받나, 안에서 직접 만드나 | 생성자/주입으로 받음 | 본문에 `new`·`Find`·`GetComponent`·싱글톤 직접 호출 |
| 남의 내부까지 파고드나 | 바로 옆 객체에게만 말 검 | `a.b.c.d` 깊은 체이닝 (내부 바뀌면 부르는 쪽 다 깨짐) |
| 한 곳 고치면 끝나나 | 지식이 한 곳에만 | 같은 로직·규칙이 여러 곳에 복붙 |

### 3-2. 이해 비용 (처음 보는 사람이 30초에 흐름을 따라가나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|-----------|------|------|
| 흐름이 한 문장으로 정의되나 | 화살표 한 줄로 이어짐 | "그리고/또"가 계속 붙음(책임 분산) |
| 클래스·메서드가 한 줄로 설명되나 | 역할이 분명 | 이름만 보고 추측해야 함 |
| 이름이 의도를 드러내나 | 읽으면 뜻이 옴 | `a`,`tmp`,`data` 남발 |
| 함수가 한 가지 일만 하고 짧나 | 짧고 단일 작업 | 길고 여러 일을 섞음 |

### 3-3. 교체/삭제 용이 (기능 하나 빼거나 갈아끼울 때 깔끔히 떨어지나)
> 잘 지워지면 = 결합이 약하다는 증거. "이거 지우면 몇 개 파일이 같이 무너지나"가 적을수록 좋은 설계다.

| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|-----------|------|------|
| 주변을 가짜로 갈아끼워 격리 테스트되나 | 의존성 주입으로 격리 가능 | 내부에서 `new`·싱글톤·실제 Animator 직접 호출 |
| 새 종류를 추가할 때 기존 코드를 안 고치나 | 데이터/구현 추가만으로 늘어남 | 새 종류마다 기존 `switch`/`if`에 분기 덧댐 |
| 비핵심이 빠져도 핵심은 도나 | 핵심 1~2개만 있으면 동작, 비핵심 없으면 건너뜀 | 비핵심 하나 없어도 NullReference로 전체 멈춤 |

### 3-4. 과설계 없음 (YAGNI — 안 쓰는 걸 미리 만들지 않았나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|-----------|------|------|
| 지금 요구만큼만 만들었나 | 필요한 만큼만 | 안 올 확장까지 미리 구현, 패턴 억지 끼움 |
| 쓰지도 않는 추상화가 없나 | 추상화에 실제 쓰임이 있음 | 구현 1개뿐인 인터페이스/팩토리, 호출 1곳뿐인 레이어 |
| 같은 일을 더 짧게 쓸 수 있나 | 군더더기 없음 | 불필요한 임시변수·과한 래핑 |

### 3-5. 유니티 함정 (엔진 특성상 유지보수를 터뜨리는 지점 — 해당될 때만)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|-----------|------|------|
| 구독·해제 짝이 맞나 | OnEnable 구독만큼 OnDisable 해제 | 해제 누락 → 누수·다중 발동 |
| 코루틴·async가 파괴/전환 시 정리되나 | Stop/Cancel로 정리, 예외 드러남 | 미정지로 잔존, 예외 묻힘 |
| static·싱글턴이 씬 객체를 붙들지 않나 | 정적 참조를 제때 끊음 | static이 씬 오브젝트 붙들어 GC 불가 |
| 파괴된 객체와 진짜 null을 구분하나 | 파괴는 `== null`, 순수 null은 `ReferenceEquals` | 파괴된 객체를 살아있다 착각 |

## 4. 평가 결과 생성

- 시스템 폴더에 `시스템명_평가.md` 형태로 파일을 생성한다. (폴더를 모르면 사용자에게 질문.)
- **판정표 1개**와 **문제·개선 방향**을 작성한다.

### 4-1. 판정표
- `## 3. 평가`의 모든 핵심 질문을 하나도 빠뜨리지 않고 옮긴다. (냄새 없으면 `해당없음`)
- 각 행을 `좋음`/`나쁨`/`해당없음`으로 판정하고, **그 판정 이유**를 같은 칸에 붙인다.

| [**좋음/나쁨/해당없음**] 핵심 질문 | 이유 + 피드백 |
|-----------|--------------------|
| | |

### 4-2. 문제와 개선 방향
- 좋은 점, 강화하면 좋은 방향을 적는다.
- **문제·단점·약점·비판을 좋은 점보다 더 구체적으로** 적는다.
- 문제는 항상 개선/해결 방법과 함께 적는다.
