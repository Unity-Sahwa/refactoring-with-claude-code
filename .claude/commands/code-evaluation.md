# 코드 평가

작성된 코드가 **좋은 코드인지** 항목별로 점검한다.
아래 `0 → 1 → 1.5 → 2 → 3` 순서를 지키고, 각 단계의 산출 형식을 그대로 따른다.

## 0. 수행 규칙 (반드시 지킬 것)

- 소스를 **직접 읽고** 평가한다. 임의로·대충·추측하지 않는다.
- 클래스·메서드는 **하나도 건너뛰지 않는다.** 개수를 세어 그 수대로 평가한다.
- 각 평가 항목 표의 **모든 행(`기준`)** 에 대해 판정한다. 행을 빠뜨리지 않는다.
- `## 2`의 `###` 항목은 **위에서부터 순서대로** 진행한다.


---

## 1. 평가 전 — 먼저 질문 (질문표)

- 평가를 시작하기 전에 아래를 **하나씩** 묻는다. 한 번에 몰아서 묻지 않는다.
- 답을 받아야 평가가 정확해진다. 특히 `소스`(경로)가 없으면 평가를 시작하지 않는다.

| 묻는 것 | 질문 |
|---------|------|
| 소스 | 시스템에 해당하는 폴더, 파일 경로를 넘겨라 |
| 목적 | 이 코드는 무엇을 하려고 짠 것인가? |
| 재사용 | 이 시스템만 쓰나, 다른 데서도 쓰나? |
| 확장 계획 | 지금 확정된 확장이 있나, 아니면 나중 일인가? |
| 규모 | 동시에 몇 개나 움직이나? (수십 개 ↔ 수만 개) |

---

## 1.5. 사전 점검 — 주석 (체크포인트)

- 본 평가(`## 2`) **전에** 주석 상태만 따로 본다. 이 단계는 **중단이 아니라 체크포인트**다 — 멈춰도 다시 처음부터 받지 않고, 주석만 손본 뒤 `## 2`로 **이어서** 간다.
- 각 클래스, 클래스 내의 각 메서드에 작성된 주석을 분석하고 표대로 평가한다.
- 각 클래스를 넘버링하고(1,2,3), 메서드 또한 넘버링하기(1-1,1-2,2-1,2-2,2-3...). 총합 개수를 적어 둔다.
- 절대로 임의로·대충·추측하지 않는다. 클래스·메서드 하나씩 건너뛰지 말고 **개수대로** 한다.
- 결과에 따라 갈라진다:
  - **주석이 충분하면** 멈추지 말고 바로 `## 2`로 진행한다.
  - **부실한 곳이 있으면** 거기서 멈추고, 어느 클래스·메서드 주석이 부족한지 보여준 뒤 사용자에게 묻는다: "주석을 보완하겠나, 이대로 진행하겠나?"
    - 사용자가 **보완하면** → 고쳐진 주석을 다시 확인하고 `## 2`로 **이어서** 진행한다(앞 단계 반복 없음).
    - 사용자가 **그대로 진행하라면** → "주석 부족 상태로 코드만 보고 판정함"이라고 적고 `## 2`로 넘어간다.
- 이 항목은 **채팅으로만** 남기고, 종합표(`3-1`)에는 **참고치로만** 적는다(점수 합산 제외).

| 질문 | 좋음 | 나쁨 |
|------|------|------|
| 클래스 `책임(역할)`에 대한 주석이 있는가 | 있음 | 없음 |
| 클래스 `확장성`에 대한 주석이 있는가 | 있음 | 없음 |
| 각 메서드의 `호출 조건`이 주석으로 있는가 | 있음 | 없음 |
| 각 메서드의 `왜`가 주석으로 있는가 | 있음 | 없음 |

## 2. 평가

- 주석은 `## 1.5`에서 이미 봤다. 여기서는 **구조만** 본다. 주석 부실을 이유로 멈추지 않는다.

### 정의
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 흐름 정의 | 시스템 전체 흐름이 정의돼 있나 | 단계가 순서로 이어져 정의됨 | 흐름이 적혀 있지 않음 | 호출 순서를 코드에서 직접 따라가야만 알 수 있음 |
| 단위 정의 | 각 클래스·메서드가 한 줄로 설명되나 | 한 줄 역할이 분명 | 무슨 일 하는지 불명 | 이름만 보고 추측해야 함 |

### 가독성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 코드 규칙 | 일관된 코드 규칙을 따랐나 | 네이밍·구조가 일관됨 | 규칙이 제각각 | 파일마다 스타일이 다름 |
| 변수명 | 변수명이 읽기 쉬운가 | 의도가 드러나는 이름 | 약어·모호한 이름 | a, tmp, data 남발 |
| 함수 길이 | 함수 길이가 적절한가 | 한 가지 일만 하고 짧음 | 길고 여러 일을 함 | 수백 줄짜리 메서드 |
| 의도 주석 | 코드로 안 읽히는 의도가 주석으로 있나 | 의도가 설명됨 | 의도 주석 없음 | 무엇만 적고 왜는 없음 |
| 개선 여지 | 더 읽기 쉽게 고칠 여지가 없나 | 더 손댈 곳이 안 보임 | 명백히 더 쉽게 쓸 수 있음 | 습관대로 써서 더 단순한 표현을 놓침 |

### 확장성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 예상 변화 대응 | 올 만한 변화에 기존 코드를 얼마나 고치나 | 새 기능 추가 시 기존 코드 거의 안 건드림 | 작은 변화에도 여러 곳을 함께 고침 | 변화 방향을 안 정하고 "전부 다 열어둠" |

### 간결성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 단순함 | 지금 요구에 비해 과한 구조가 없나 | 지금 필요한 만큼만 만듦 | 안 쓰는 유연성을 미리 넣음 | 안 올 확장까지 미리 구현(과설계), 패턴을 억지로 끼움 |
| 더 짧게 | 같은 일을 더 짧게 쓸 수 있나 | 군더더기 없음 | 같은 동작을 더 줄일 수 있음 | 중복 분기·불필요한 임시변수·과한 래핑 |

### 재사용성
- 결합도(파급 범위)는 `DIP-느슨한 결합`에서 본다. 여기서는 **함수 단위 재사용**만 본다.

| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 함수 분리 | 함수가 역할대로 분리돼 재사용되나 | 한 함수가 한 일만 해 떼어 쓸 수 있음 | 한 함수가 여러 일을 묶어 못 떼어냄 | 복붙으로 같은 로직이 여러 곳에 |

### 테스트 용이성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 테스트 용이성 | 주변을 가짜로 갈아끼워 따로 테스트되나 | 의존성을 주입받아 격리 가능 | 내부에서 직접 만들어 격리 불가 | 내부에서 `new`, 싱글톤, 실제 Animator/엔진 직접 호출 |
| 디버깅 용이성 | 문제 생겼을 때 흐름 추적이 쉽나 | 데이터·호출 흐름이 명확 | 추적이 어려움 | 숨은 의존·전역 상태, 트리거가 여러 곳에 흩어짐 |
| 부재 견딤 | 구성 요소 하나가 없어도 안 터지나 | 요소가 없으면 건너뛰고 동작 | 요소 없으면 NullReference로 터짐 | 주입·참조가 null인 채 바로 사용, null 체크 없음 |

### 성능/비용
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 매 프레임 비용 | 매 프레임 도는 연산이 가벼운가 | 필요할 때만 돌고 안 쓰면 멈춤 | 항상 전량을 순회 | 비활성 상태에도 Update/FixedUpdate가 계속 돎 |
| 메모리 할당 | 런타임에 GC 스파이크를 안 만드나 | 버퍼·풀을 재사용(NonAlloc) | 매 프레임 new로 할당 | 매 프레임 배열·람다·클로저 할당 |
| 규모 대응 | 동시 수가 늘어도 견디나 | 수에 비례해 완만하게 증가 | 수가 늘면 급격히 무거워짐 | O(n^2) 검사, 매번 전수 Find |
| 개선 여지 | 더 빠르게·가볍게 고칠 여지가 없나 | 더 손댈 곳이 안 보임 | 명백히 더 효율적으로 쓸 수 있음 | 같은 계산·재탐색을 캐시 안 하고 반복 |

### OCP (개방-폐쇄 원칙)

|------|-----------|------|------|-----------|
| 확장 개방·수정 폐쇄 | 새 종류를 추가할 때 기존 코드를 안 고치고 늘리나 | 인터페이스·데이터로 추가만 하면 됨 | 새 종류마다 기존 코드를 수정 | 종류가 늘 때마다 기존 switch/if에 분기를 덧댐 |

| 인터페이스 분리 | 구현체가 안 쓰는 멤버까지 강요받지 않나 | 역할별로 잘게 나뉜 인터페이스 | 비대한 인터페이스에 빈 구현이 생김 | 거대 인터페이스 하나에 전부 몰기 |

|------|-----------|------|------|-----------|
| 다형성 활용 | 같은 약속을 여러 구현이 다르게 채우나 | 부르는 쪽은 누가 하든 똑같이 호출 | 종류마다 if/switch 분기 | 전환·행동 규칙을 if-else 떡칠로 처리 |

## 3. 평가 결과 — 이렇게 쓴다

모든 항목을 마치면 아래 **표 1개**와 **문제·개선 방향**으로 정리한다. 산문으로 길게 풀지 않는다.

- 결과는 **채팅에 출력하고, 동시에 평가 대상 시스템 폴더에 파일로 저장한다.**
- 저장 위치: `## 1`에서 받은 `소스` 폴더 (예: `Assets/.../SkillMove/`).
- 파일명: `시스템명_평가.md` (예: `SkillMove_평가.md`). 시스템명은 `## 1`에서 받은 소스 폴더명을 쓴다. 같은 이름이 있으면 덮어쓴다(최신 1개만 유지).
- 파일에는 아래 `3-1` 표와 `3-2` 문제·개선 방향만 담는다.

### 3-1. 판정표
- `## 2`의 모든 기준(핵심 질문)을 **하나도 빠뜨리지 않고** 한 표에 옮긴다.
- 각 행은 `좋음`인지 `나쁨`인지 판정하고, **그렇게 판정한 이유**를 같은 칸에 붙여 적는다.

| 핵심 질문 | 좋음/나쁨. 그 이유 |
|-----------|--------------------|
| (예) 시스템 전체 흐름이 정의돼 있나 | 나쁨. 호출 순서가 코드에 흩어져 직접 따라가야 알 수 있음 |

### 3-2. 문제와 개선 방향
- **문제·단점을 장점보다 더 많이, 더 구체적으로, 기계적으로** 적는다.
- `지금 고칠 것`을 위에, `나중에 봐도 될 것`을 아래에 둔다.

| 우선순위 | 무엇이 문제인가 | 어떻게 고치나 |
|----------|-----------------|----------------|
| 지금 고칠 것 | | |
| 나중에 봐도 될 것 | | |
