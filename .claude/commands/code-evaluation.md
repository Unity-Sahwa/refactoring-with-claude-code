## 0. 수행 규칙 (반드시 지킬 것)
- `1 → 2 → 3 → 4` 순서대로 진행한다
- 소스를 **직접 읽고** 평가한다. 임의로·대충·추측하지 않는다.
- 추측해서 평가하지 않는다. 주석과 코드의 정보만으로 솔직하고 기계적으로 평가한다.

---

## 1. 평가 전 — 먼저 질문 (질문표)

- 평가를 시작하기 전에 아래를 **하나씩** 묻는다. 한 번에 몰아서 묻지 않는다.
- 답을 받아야 평가가 정확해진다. 특히 `소스`(경로)가 없으면 평가를 시작하지 않는다.

| 묻는 것 | 질문 |
|---------|------|
| 소스 | 시스템에 해당하는 폴더, 파일 경로를 넘겨라 |

## 2. 주석 확인
- 아래 형식으로 각 클래스의 주석의 존재 유무를 확인한다.
| 질문 | O/X |
|------|------|
| `흐름` | O/X |
| `책임(역할)/용도` | O/X |
| `확장성` | O/X |
| `작동 예시` | O/X |
(작동 예시란 실제 플레이에서 해당 시스템이 어떻게 작동하는지를 의미함)

- 아래 형식으로 각 메서드의 주석의 존재 유무를 확인한다.
| 질문 | O/X |
|------|------|
| `호출 조건` | O/X|
| `왜` | O/X |

- 채팅창에 각 클래스(메서드 포함)의 확인표를 생성한다.
- 사용자와 피드백을 반복한다.
- 피드백이 끝나면 다음 단계로 넘어간다.

## 3. 평가

### 정의
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 흐름 정의 | 시스템 전체 흐름이 한 문장으로 정의돼 있나 | 단계가 화살표 한 줄로 이어짐 (예: Rent→부착→Setup→켜기→수명→Return) | 흐름이 갈래쳐 한 줄로 안 됨 | 책임이 흩어져 설명에 "그리고/또"가 계속 붙음 |
| 단위 정의 | 각 클래스·메서드가 한 줄로 설명되나 | 한 줄 역할이 분명 | 무슨 일 하는지 불명 | 이름만 보고 추측해야 함 |


### 가독성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 코드 규칙 | 일관된 코드 규칙을 따랐나 | 네이밍·구조가 일관됨 | 규칙이 제각각 | 파일마다 스타일이 다름 |
| 변수명 | 변수명이 읽기 쉬운가 | 의도가 드러나는 이름 | 약어·모호한 이름 | a, tmp, data 남발 |
| 함수 길이 | 함수 길이가 적절한가 | 한 가지 일만 하고 짧음 | 길고 여러 일을 함 | 수백 줄짜리 메서드 |

### 간결성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 단순함 | 지금 요구에 비해 과한 구조가 없나 | 지금 필요한 만큼만 만듦 | 안 쓰는 유연성을 미리 넣음 | 안 올 확장까지 미리 구현(과설계), 패턴을 억지로 끼움 |
| 더 짧게 | 같은 일을 더 짧게 쓸 수 있나 | 군더더기 없음 | 같은 동작을 더 줄일 수 있음 | 중복 분기·불필요한 임시변수·과한 래핑 |

### 재사용성
- 결합도(파급 범위)는 `DIP-느슨한 결합`에서 본다. 여기서는 **함수 단위 재사용**만 본다.

| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 함수 분리 | 함수가 역할대로 분리돼 재사용되나 | 한 함수가 한 일만 해 떼어 쓸 수 있음 | 한 함수가 여러 일을 묶어 못 떼어냄 | 복붙으로 같은 로직이 여러 곳에 |

### 테스트 용이성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 테스트 용이성 | 주변을 가짜로 갈아끼워 따로 테스트되나 | 의존성을 주입받아 격리 가능 | 내부에서 직접 만들어 격리 불가 | 내부에서 `new`, 싱글톤, 실제 Animator/엔진 직접 호출 |
| 디버깅 용이성 | 문제 생겼을 때 흐름 추적이 쉽나 | 데이터·호출 흐름이 명확 | 추적이 어려움 | 숨은 의존·전역 상태, 트리거가 여러 곳에 흩어짐 |
| 핵심 외 부재 견딤 | 핵심(꼭 필요한 것)만 빼고 나머지는 없어도 핵심 기능이 안 터지고 도나 | 핵심 1~2개만 있으면 되고, 비핵심 없으면 건너뛰고 핵심은 실행 | 비핵심 하나 없어도 NullReference로 터지거나 전체가 멈춤 | 부수 의존까지 전부 필수로 박음, 없으면 null 채로 사용·`return`으로 전체 중단 |


### 성능/비용
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 매 프레임 비용 | 매 프레임 도는 연산이 가벼운가 | 필요할 때만 돌고 안 쓰면 멈춤 | 항상 전량을 순회 | 비활성 상태에도 Update/FixedUpdate가 계속 돎 |
| 메모리 할당 | 런타임에 GC 스파이크를 안 만드나 | 버퍼·풀을 재사용(NonAlloc) | 매 프레임 new로 할당 | 매 프레임 배열·람다·클로저 할당 |
| 규모 대응 | 동시 수가 늘어도 견디나 | 수에 비례해 완만하게 증가 | 수가 늘면 급격히 무거워짐 | O(n^2) 검사, 매번 전수 Find |
| 개선 여지 | 더 빠르게·가볍게 고칠 여지가 없나 | 더 손댈 곳이 안 보임 | 명백히 더 효율적으로 쓸 수 있음 | 같은 계산·재탐색을 캐시 안 하고 반복 |

### SRP (단일 책임 원칙)
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 책임 분리 | 한 **객체**가 한 가지 책임(=바뀌는 이유)만 지나 | 여러 일을 해도 바뀌는 이유가 하나면 단일 책임 | 서로 다른 이유로 바뀌는 코드가 한 객체에 섞임 | 기능(하는 일) 개수로 책임을 셈 — 일이 많아도 이유가 하나면 위반 아님 |

### OCP (개방-폐쇄 원칙)
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 확장 개방·수정 폐쇄 | 새 종류를 추가할 때 기존 코드를 안 고치고 늘리나 | 인터페이스·데이터로 추가만 하면 됨 | 새 종류마다 기존 코드를 수정 | 종류가 늘 때마다 기존 switch/if에 분기를 덧댐 |

### LSP (리스코프 치환 원칙)
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 치환 가능성 | 자식이 부모 자리에 들어가도 규약이 안 깨지나 | 어떤 구현이 와도 부르는 쪽은 동일하게 동작 | 특정 자식에서 예외·오작동 | 자식이 부모 메서드를 비워두거나 throw로 막음 |

### ISP (인터페이스 분리 원칙)
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 인터페이스 분리 | 구현체가 안 쓰는 멤버까지 강요받지 않나 | 역할별로 잘게 나뉜 인터페이스 | 비대한 인터페이스에 빈 구현이 생김 | 거대 인터페이스 하나에 전부 몰기 |

### DIP (의존 역전 원칙)
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 느슨한 결합 | 객체끼리 약속(인터페이스)으로 연결되나 | 인터페이스/추상으로 간접 연결 | 구체 클래스끼리 직접 호출 | 클래스 직접 결합, 구체 enum 값에 직접 의존 |
| 의존성 주입 | 필요한 것을 밖에서 받아오나 | 주입으로 받음 | 내부에서 직접 생성·검색 | `Activator.CreateInstance`·`Find`로 직접 조달, 싱글톤 자기 노출 |

### 캡슐화
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 캡슐화 | (MonoBehaviour 클래스 중에서) 내부 상태를 숨기고 정해진 통로로만 다루나 | 상태는 감추고 메서드로만 접근 | 내부 값을 밖에서 직접 만지게 열어둠 | 테스트 용도 외에 Inspector로 직접 변수 받기(`[SerializeField]`/`public`), `protected` 날 필드 직접 대입 |

### 다형성
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 다형성 활용 | 같은 약속을 여러 구현이 다르게 채우나 | 부르는 쪽은 누가 하든 똑같이 호출 | 종류마다 if/switch 분기 | 전환·행동 규칙을 if-else 떡칠로 처리 |

### 씬 전환
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 씬 전환 안전성 | 씬이 바뀔 때 잔존·누수·에러 없이 정리되나 | 켜져 있던 것들이 깔끔히 정리되고 참조가 끊기지 않음 | 씬 넘으면 객체가 남거나 참조가 끊겨 null로 터짐 | DontDestroyOnLoad로 살린 객체가 씬별 객체를 참조(dangling), 풀·핸들 미해제로 누수 |

### 유니티 함정
| 기준 | 핵심 질문 | 좋음 | 나쁨 | 흔한 함정 |
|------|-----------|------|------|-----------|
| 구독 짝 맞춤 | 이벤트 구독과 해제가 짝이 맞나 (활성/비활성 반복에 중복 구독 안 쌓이나) | 구독한 만큼 정확히 해제, 중복 없음 | 해제 누락으로 누수·다중 발동 | OnEnable 구독 후 OnDisable 해제 누락 / 토글마다 재구독 |
| 비동기 정리 | 코루틴·async가 상태 전환·파괴 시 취소되고 오류가 안 삼켜지나 | 중단점에서 Stop/Cancel로 정리, 예외 드러남 | 멈춰야 할 때 계속 돎, 예외 묻힘 | 코루틴 미정지로 잔존, try-catch 불가로 오류 무시 |
| 유니티 null 비교 | 파괴된 객체와 진짜 null을 구분해 다루나 | 파괴 판정은 `== null`, 순수 null은 `ReferenceEquals` | 의미를 섞어 오판 | 파괴된 객체를 살아있다고 착각 |
| 정적 참조 수명 | static·싱글턴이 씬 객체를 붙들어 누수 안 만드나 | 정적 참조를 제때 끊음 | 정적이 씬 객체를 참조해 GC 불가 | static 필드가 씬 오브젝트를 계속 붙듦 |

## 4. 평가 결과 생성

- 시스템 폴더에 `시스템명_평가.md` 형태로 파일을 생성한다.(시스템 폴더를 모르면 사용자에게 질문한다.)
- **판정표 1개**와 **문제·개선 방향**을 해당 파일에 작성한다

### 4-1. 판정표
- `## 3. 평가`의 모든 기준(핵심 질문)을 **하나도 빠뜨리지 않고** 판정표에 옮긴다.
- 각 행은 `좋음`인지 `나쁨`인지 판정하고, **그렇게 판정한 이유**를 같은 칸에 붙여 적는다.

| [**좋음/나쁨**]핵심 질문 | 이유 + 피드백|
|-----------|--------------------|
| | |

### 4-2. 문제와 개선 방향
- 좋은 점, 강화하면 좋은 방향을 적는다.
- **문제, 단점, 약점, 비판을 좋은점, 강화하면 좋은 방향보다 더 구체적으로** 적는다.
- 문제, 단점, 약점, 비판은 항상 개선/해결 방법, 방향과 함께 적는다.
