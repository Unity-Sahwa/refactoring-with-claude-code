## 0. 절차 (반드시 지킬 것)

1. 대상 `.cs` 파일을 **직접 읽고** 평가한다. 추측·간소화하지 않는다.
2. 1절 축으로 평가한다. 냄새가 안 보이면 그 행은 `해당없음`으로 적는다(억지 평가 금지).
3. 2절 형식의 판정표를 출력한다.
4. **코드를 수정하지 않는다. 보고만 한다. 파일도 만들지 않는다.**

- 네이밍·서식 위반은 여기서 다루지 않는다 (`code-convention` 담당).
- 주석 위반은 여기서 다루지 않는다 (`comment-convention` 담당).
- `Old/`, `_Test`, `PerformanceTest`는 제외한다.
- 엄격하고 진지하게, 중립적으로 판단한다.

## 1. 평가 축

### 1-1. 변경 파급 (이거 하나 고치면 몇 군데가 깨지나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|---|---|---|
| 의존을 밖에서 받나, 안에서 직접 만드나 | 주입으로 받음 | 본문에 `new`·`Find`·`GetComponent`·싱글톤 직접 호출 |
| 남의 내부까지 파고드나 | 바로 옆 객체에게만 말 검 | `a.b.c.d` 깊은 체이닝 |
| 한 곳 고치면 끝나나 | 지식이 한 곳에만 | 같은 로직·규칙이 여러 곳에 복붙 |
| 튜닝 수치가 제자리에 있나 | 공용 값은 SO, 개체별 값은 `[SerializeField]` | 공용 값이 코드 매직넘버·인스펙터에 흩어져 바꿀 때 여러 곳을 열어야 함 (기준은 System Usage Guide의 ‘수치를 어디 둘 것인가’) |

### 1-2. 이해 비용 (처음 보는 사람이 30초에 흐름을 따라가나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|---|---|---|
| 흐름이 한 문장으로 정의되나 | 화살표 한 줄로 이어짐 | "그리고/또"가 계속 붙음(책임 분산) |
| 함수가 한 가지 일만 하고 짧나 | 짧고 단일 작업 | 길고 여러 일을 섞음 |
| 인자 수가 적나 | 3개 이하 | 인자가 계속 늘어남 |
| 메서드가 이름에 없는 일을 하나 | 이름대로만 동작 | 이름에 없는 외부 상태를 바꿈(사이드 이펙트) |
| bool 플래그로 모드를 가르나 | 이름이 다른 두 메서드 | `GetAngle(bool inDegrees)` |
| 타입이 보이나 | `var x = new Player()` | `var data = LoadData()` — 타입 불명확 |

### 1-3. 교체/삭제 용이 (기능 하나 빼거나 갈아끼울 때 깔끔히 떨어지나)
> 잘 지워지면 = 결합이 약하다는 증거. "이거 지우면 몇 개 파일이 같이 무너지나"가 적을수록 좋다.

| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|---|---|---|
| 주변을 가짜로 갈아끼워 격리 테스트되나 | 주입으로 격리 가능 | 내부에서 `new`·싱글톤·실제 Animator 직접 호출 |
| 새 종류를 추가할 때 기존 코드를 안 고치나 | 데이터/구현 추가만으로 늘어남 | 새 종류마다 기존 `switch`/`if`에 분기 덧댐 |
| 비핵심이 빠져도 핵심은 도나 | 비핵심 없으면 건너뜀 | 비핵심 하나 없어도 NullReference로 전체 멈춤 |

### 1-4. 과설계 없음 (YAGNI — 안 쓰는 걸 미리 만들지 않았나)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|---|---|---|
| 지금 요구만큼만 만들었나 | 필요한 만큼만 | 안 올 확장까지 미리 구현, 패턴 억지 끼움 |
| 쓰지도 않는 추상화가 없나 | 추상화에 실제 쓰임이 있음 | 구현 1개뿐인 인터페이스/팩토리, 호출 1곳뿐인 레이어 |
| 같은 일을 더 짧게 쓸 수 있나 | 군더더기 없음 | 불필요한 임시변수·과한 래핑 |

### 1-5. 유니티 함정 (엔진 특성상 유지보수를 터뜨리는 지점 — 해당될 때만)
| 핵심 질문 | 좋음 | 나쁨 (=찾는 냄새) |
|---|---|---|
| 구독·해제 짝이 맞나 | `OnEnable` 구독만큼 `OnDisable` 해제 | 해제 누락 → 누수·다중 발동 |
| 코루틴·async가 파괴/전환 시 정리되나 | Stop/Cancel로 정리, 예외 드러남 | 미정지로 잔존, 예외 묻힘 |
| static·싱글턴이 씬 객체를 붙들지 않나 | 정적 참조를 제때 끊음 | static이 씬 오브젝트 붙들어 GC 불가 |
| 파괴된 객체를 살아있다 착각하지 않나 | `UnityEngine.Object`는 `== null`로 검사 | `_animator?.` — `?.`는 파괴 감지를 우회함 |

> `?.`는 C# 연산자라 유니티가 오버로드한 `== null`(파괴 감지)을 타지 않는다.
> 단 `OnDied?.Invoke()` 같은 순수 C# event·객체에는 `?.`를 써도 된다.

## 2. 판정표 출력

1절의 모든 핵심 질문을 하나도 빠뜨리지 않고 옮긴다.

| 판정 | 축 | 핵심 질문 | 근거 (파일:줄) |
|---|---|---|---|
| 나쁨 | 1-1 | 의존을 밖에서 받나 | PlayerMove.cs:22 — `FindObjectOfType<AudioPlayer>()` 직접 호출 |
| 해당없음 | 1-5 | 코루틴 정리 | 코루틴 없음 |

- 판정은 `좋음` / `나쁨` / `해당없음` 셋 중 하나.
- `나쁨`에는 반드시 파일:줄 근거를 적는다. 근거 없으면 적지 않는다.

그 아래에 **문제와 개선 방향**을 적는다.
- 좋은 점, 강화하면 좋은 방향을 적는다.
- **문제·단점·약점을 좋은 점보다 더 구체적으로** 적는다.
- 문제는 항상 개선 방법과 함께 적는다.
