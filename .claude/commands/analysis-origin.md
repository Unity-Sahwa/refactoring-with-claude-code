# 1. 수집
## 주제 선정
- 사용자에게 어떤 주제로 진행할지 질문하기
- 사용자에게 기존 코드 위치를 올려달라고 질문하기
- claude는 `Assets/1.Code/Scripts` 하위의 해당 시스템 폴더 안에 파일을 생성하여 기존 코드를 분석하여 작성. (해당 시스템 폴더가 없으면 만든다.)
- 아래의 형식으로 작성한다. 그 외엔 작성하지 않는다.

## 형식
```
## 기존 코드 위치 및 역할
| 위치 | 역할 |
| --- | --- |
| A | AA |

```
### 기존 코드 위치 및 역할
- 위치 단위는 `클래스명.메서드명()`이다.
    ex) PlayerSkillMove.SkillMove(...)
    ex) PlayerSkillMove.RayCastForward()
    ex) PlayerSkillMove.MoveSwitch(...)
- 위치 항목에는 줄번호, 클래스명.cs 같은걸 적지 않는다.
- 각 위치에는 클릭해서 이동할 수 있는 링크가 있어야 한다.

- 역할 작성은 아래와 같이 작성한다.
    - 역할은 입력값·동작·결과가 드러나게 1~2줄로 쓴다. 쉬운 말로 풀되, 메서드가 받는 값과 하는 일을 구체적으로 적는다.
    - 예) SkillMove(...) → "스킬 이동 정보(대기시간·지속시간·방향·속도)를 받아, 대기시간이 지나면 그 방향으로 이동을 켜고, 지속시간이 끝나면 다시 꺼서 멈추는 코루틴 메서드."

## 형식

### 기능 필요성
- 이 시스템이 왜 필요한지 1문단으로 쓴다. (코드가 아니라 기능 관점)

### 필요한 기능
- 필요한 기능을 번호로 나누고, 각 기능 아래에 설명을 bullet로 단다.
- 구현 방법이 떠오르면 그 방향도 함께 적는다. (예: "배열로 전달", "OverlapCapsule로 감지")

### 적용 범위
- 먼저 `Scripts-Origin` 폴더 안에서만 대상 클래스·메서드의 참조를 추적한다.
    - 클래스명·메서드명 호출처, `.Instance` 같은 싱글턴 접근을 찾아 "현재 어디서 쓰이는지"를 표나 목록으로 정리한다.
    - 한계: 텍스트로 찾는 것이라 같은 이름의 다른 메서드, 인터페이스·이벤트·상속을 거친 호출은 놓치거나 잘못 잡을 수 있다. 확신 안 서는 항목은 (확인 필요)로 표시한다.
- 위 추적 결과를 근거로 이 시스템을 어디까지 적용할지 정한다. (과한 설계 방지용)
    - 추적 결과(현재 쓰이는 곳)와 적용 범위(앞으로 만들 곳)는 다르다. 추적은 판단 근거일 뿐 그대로 범위가 되지 않는다.
- 공용으로 묶을 부분과 대상별로 갈라야 할 부분을 구분한다.

### 예상 문제
- 기존 코드의 문제가 아니라, "이 기능이 이대로 가면 생길 문제"를 적는다.
- 각 문제마다 해결 방향을 함께 적는다. (코드를 고치라는 게 아니라, 설계 때 피할 방향)
- 검토했지만 제외한 방법이 있으면 이유와 함께 남긴다.
