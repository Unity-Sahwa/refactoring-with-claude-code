# 히트박스 / 전투 시스템 설계 평가

## 평가 범위
- `Assets/1.Code/Scripts/CombatSystem/` 전체
- `Assets/1.Code/Scripts/PlayerSystem/Hitbox/` 전체
- `Assets/1.Code/Scripts/DataSystem/HitboxDataEntry.cs`, `IHitboxCombat.cs`, `IPlayerHitbox.cs`

## 전제 (사용자 확정)
1. 적도 이 히트박스 시스템을 쓴다. (적 확장은 "나중 일"이 아니라 확정)
2. 전투 시 적 약 10마리가 동시에 히트박스 사용. 여러 마리가 같은 형태 히트박스를 쓸 수 있어 **Provider 재설계 필요**(사용자 인지).
3. 켜진 히트박스는 매 물리 스텝(FixedUpdate) OverlapNonAlloc로 판정한다.
4. 앞으로 자주 바뀔 부분은 피격 효과 종류(`IHitReaction` 구현체).

## 축 1 — 좋은 설계인가

| 기준 | 충족? | 근거 |
|------|-------|------|
| 단순함 | △ | 켜기/전투 관심사를 인터페이스로 나눈 건 적절. 단 `IHitReaction`을 빈 마커 인터페이스로 둬, 받는 쪽이 `GetType()`으로 종류를 까봐야 함 → 지금 요구(넉백·상태이상 2종)엔 과한 구조 |
| 예상 변화 대응 | △ | 효과 추가는 타입만 추가하면 됨(좋음). 하지만 적 확장이 확정인데 핸들러가 `PlayerHitboxHandler` 하나뿐이고 `_targetMask`를 생성자에서 하드코딩 → 적 추가 시 이 클래스를 고쳐야 함 |
| 낮은 결합 | ✅ | Reporter는 `IHitboxCombat`만 읽고 상대를 모름. `IDamageable`로만 전달. 한쪽 수정이 번지지 않음 |
| 책임 분리(시스템) | ✗ | `HitboxProvider`가 너무 많은 일을 함 — 데이터 순회(BaseStateData) + Addressable 로딩 + 풀링 + MeshRenderer 캐싱 + Reporter 캐싱. 5가지 책임 |
| 테스트 용이성 | ✗ | Provider가 `Addressables.LoadAssetAsync`를 내부에서 직접 호출 → 엔진 없이 격리 불가. Reporter도 `Physics.Overlap*` 직접 호출 |
| 디버깅 용이성 | ✅ | 흐름이 한 방향(데이터→핸들러→Reporter→DamageInfo→대상). Gizmo·더미로 가시화까지 갖춤 |

### 🔴 가장 위험한 문제 — Provider "키당 1개" 가정 붕괴 (전제 2로 확정)
`HitboxProvider`는 `_instances[key] = instance`로 키당 인스턴스 1개만 만들고, `Rent`는 매번 같은 걸 돌려준다.
- 적 10마리가 같은 히트박스를 동시에 켜면 → 한 GameObject를 10마리가 공유.
- transform이 마지막 부모로 끌려가고, `Setup(combat, damager…)`이 서로 덮어쓰며, `_alreadyHit` 집합도 공유됨 → 판정이 완전히 엉킴.
- 현재는 플레이어 1명이라 안 터질 뿐. **적 확장 즉시 터지는 구조적 결함.**

### 🟠 두 번째 — God 클래스화된 Provider
로딩·풀·캐싱·데이터순회가 한 곳에 뭉쳐, 위 멀티 인스턴스 풀로 바꿀 때 이 한 클래스를 통째로 손대야 한다.

## 축 2 — 객체지향인가

| 기준 | 충족? | 근거 |
|------|-------|------|
| 캡슐화 | ✅ | 전투값은 `[SerializeField] private` + 읽기 프로퍼티. Reporter는 값을 `Setup`으로만 주입받음(인스펙터 직접 노출 안 함) |
| 책임 분리(객체) | △ | Reporter·AttachPoint·DataEntry는 깔끔. 단 `PlayerHitboxHandler`가 구독·생성·코루틴 수명·캐릭터스왑 처리를 다 앎 |
| 느슨한 결합 | ✅ | 핸들러는 `IHitboxProvider`·`IHitboxAttachPoint`, Reporter는 `IHitboxCombat`·`IDamageable`로만 연결. 구체 타입 직접 호출 거의 없음 |
| 다형성 활용 | ✗ | 두 곳에서 깨짐. ① `IHitReaction`이 빈 마커라 받는 쪽이 `is KnockbackReaction` 식 분기를 강요받음(효과 늘수록 if 떡칠). ② Reporter의 `OverlapCollider`가 콜라이더 종류별 `switch` |
| 의존성 주입 | △ | 인터페이스 주입은 함. 단 `Dictionary<Type, List<object>>` + `[0]` 인덱스 + `(IHitboxProvider)` 캐스팅 → 타입 안전성 없음, 비면 런타임에 터짐 |

### 🟠 다형성 — 마커 인터페이스의 대가
`IHitReaction { }`은 데이터(효과 종류)와 처리(어떻게 미는지)를 떼려는 의도는 타당하나, 처리하는 쪽이 결국 타입 분기를 해야 한다. 효과가 5종, 10종 되면 받는 쪽마다 분기가 늘어난다. 지금은 2종이라 비용이 안 보일 뿐.

> 참고: `OverlapCollider`의 switch는 봐줄 만한 분기다. Unity의 `BoxCollider` 등은 우리가 만든 타입이 아니고 sealed라 다형성으로 못 바꾼다. 여기에 추상화를 끼우는 건 오히려 과설계.
