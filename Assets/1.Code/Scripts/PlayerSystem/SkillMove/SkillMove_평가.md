# SkillMove 평가 (PlayerSkillMoveHandler.cs)

## 4-1. 판정표

| 판정 / 핵심 질문 | 이유 + 피드백 |
|------------------|----------------|
| **[좋음]** 흐름이 한 문장으로 정의돼 있나 | 7~10번 줄 주석에 `이벤트 호출 → HandleSkillMove → 활성화 → FixedUpdate(수명·물리이동) → 만료 시 비활성화`로 화살표 한 줄 정의됨 |
| **[좋음]** 각 클래스·메서드가 한 줄로 설명되나 | 모든 메서드에 호출조건·왜 주석이 붙어 역할이 분명 |
| **[좋음]** 일관된 코드 규칙을 따랐나 | 네이밍·구조 일관됨. (경미) 14번 줄 `[Inject(true)]private`은 다른 줄과 띄어쓰기 정렬이 어긋남 |
| **[좋음]** 변수명이 읽기 쉬운가 | `localVelocity`, `worldVelocity`, `intended`, `elapsed` 등 의도가 드러남 |
| **[좋음]** 함수 길이가 적절한가 | 모든 메서드가 짧고 한 화면 내 |
| **[좋음]** 지금 요구에 비해 과한 구조가 없나 | `List<ActiveMove>`로 다중 이동을 받지만 향후 확장(주변 감지)을 위한 최소 구조. 과설계 아님 |
| **[좋음]** 같은 일을 더 짧게 쓸 수 있나 | 군더더기 거의 없음. (경미) Start의 fallback `foreach … break`는 단순화 여지 있음 |
| **[좋음]** 함수가 역할대로 분리돼 재사용되나 | FixedUpdate가 만료처리+속도합산+이동을 한 덩어리로 묶었으나 **의도된 설계**(TODO: 속도 계산을 전략으로 분리 예정). 현 시점 판정은 통과 |
| **[좋음]** 주변을 가짜로 갈아끼워 따로 테스트되나 | 의존성을 인터페이스로 주입받아 격리 가능. 단 물리이동 검증은 **유니티 에디터(PlayMode) 한정**으로 가능 |
| **[좋음]** 문제 생겼을 때 흐름 추적이 쉽나 | 이벤트 진입점·데이터 흐름이 단순해 추적 쉬움 |
| **[좋음]** 핵심만 빼고 나머지 없어도 도나 | `_eventSubscriber`·`_swapNotifier`는 선택 주입(`[Inject(true)]`)+null 체크. RB 없으면 경고 후 진행. 비핵심 부재를 견딤 |
| **[좋음]** 매 프레임 도는 연산이 가벼운가 | `_actives` 비면 `enabled=false`로 FixedUpdate 자체가 멈춤 |
| **[좋음]** 런타임에 GC 스파이크를 안 만드나 | `new ActiveMove`는 스킬 사용 시에만 발생. 매 프레임 할당 없음 |
| **[좋음]** 동시 수가 늘어도 견디나 | `_actives` 순회 O(n), n은 동시 이동 수로 작음 |
| **[좋음]** 더 빠르게·가볍게 고칠 여지가 없나 | `localVelocity`를 미리 계산해 매 프레임 재정규화 방지. 명백한 낭비 없음 |
| **[좋음]** 한 객체가 한 가지 책임만 지나 | "스킬 이동을 켜고 끄고 적용한다"는 하나의 바뀌는 이유로 묶임 |
| **[좋음]** 기존 코드 안 고치고 늘리나 | `ISkillMove` 데이터 추가만으로 새 이동 동작 추가 가능 |
| **[좋음]** 자식이 부모 자리에 들어가도 규약 안 깨지나 | `BaseCharacter<T>`, `ISkillMove` 구현 치환에 예외·오작동 없음 |
| **[좋음]** 안 쓰는 멤버까지 강요받지 않나 | `ISkillMove`(3개), `IStartData`, 구독자 인터페이스가 역할별로 잘게 분리됨 |
| **[좋음]** 객체끼리 약속으로 연결되나 | 구독·스왑·데이터 모두 인터페이스 의존. (경미) `Rigidbody`·`PlayerCharacterType`는 구체 의존 |
| **[좋음]** 필요한 것을 밖에서 받아오나 | `[Inject]`로 전부 주입. 내부 `new`/`Find` 없음 |
| **[좋음]** 내부 상태를 숨기고 정해진 통로로만 다루나 | 모든 필드 private, `[SerializeField]`/public 없음. 캡슐화 우수 |
| **[좋음]** 같은 약속을 여러 구현이 다르게 채우나 | `ISkillMove`로 다형 처리. 종류별 if/switch 분기 없음 |
| **[좋음]** 씬이 바뀔 때 잔존·누수·에러 없이 정리되나 | OnDestroy에서 구독 해제 + `_actives.Clear()`. static 미사용 |
| **[좋음]** 이벤트 구독·해제 짝이 맞나 | Awake 구독 / OnDestroy 해제. enabled 토글에도 재구독 안 해 중복 누적 없음 |
| **[좋음]** 코루틴·async가 전환·파괴 시 정리되나 | 코루틴/async 미사용. 해당 위험 없음 |
| **[좋음]** 파괴된 객체와 진짜 null을 구분하나 | `rb == null`로 파괴 판정 적절 |
| **[좋음]** static·싱글턴이 씬 객체를 붙들어 누수 안 만드나 | static 참조 없음 |
| **[나쁨]** 외부 입력 타입 안전성 | `HandleSkillMove`의 `(ISkillMove)data` 강제 캐스팅은 실패 시 모호한 `InvalidCastException`만 남김 |

## 4-2. 문제와 개선 방향

### 좋은 점 (강화 방향)
- **캡슐화·DI가 모범적**: 전 필드 private + 인터페이스 주입. 테스트·교체에 강하다. 이 패턴을 다른 핸들러에도 유지하면 좋다.
- **성능 설계가 명확**: `enabled` 토글로 비활성 시 FixedUpdate를 끄고, `localVelocity`를 사전 계산해 매 프레임 재정규화를 피한다.
- **구독/해제 짝이 정확**: Awake↔OnDestroy로 묶어 토글 반복에도 중복 구독이 쌓이지 않는다.
