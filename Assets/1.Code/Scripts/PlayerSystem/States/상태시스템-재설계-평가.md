# 상태(State) 시스템 재설계 평가

> 목표: 현재 "여러 캐릭터를 스왑하는 플레이어" 전용으로 묶인 상태 시스템을,
> 몬스터(잡몹/보스) 등 다른 캐릭터에서도 재사용할 수 있게 재설계 가능한지 평가.

## 전제 (사용자 확인 사항)

1. 몬스터는 애니메이션 진행률에 묶이지 않는다. **외부(AI)에서 "이 상태로 바꿔달라"고 요청**한다.
   → 상태 시스템은 "전환 요청을 받는 입구"가 필요하다.
2. **캐릭터 스왑은 상태 시스템과 별개**다. 캐릭터가 1개든 2개든 상관없어야 하고, 스왑은 외부에서 소통한다.
3. **제네릭(BaseState, BaseStateManager)** 은 Player/Enemy 잡몹/Enemy 보스 공용을 노린 것.
4. 재사용은 확정 아님. 몬스터를 염두에 두고 제네릭으로 만들었지만, **캐릭터 스왑을 상태 시스템 안에 넣어서 헛돌았다.**

---

## 축 1 — 좋은 설계인가

| 기준 | 판정 | 근거 (문제 위주) |
|------|------|------|
| 단순함 | 미흡 | 안 올 수도 있는 확장(보스)을 위해 `ECharacter` 제네릭을 깔아 매니저·상태·딕셔너리 시그니처를 전부 오염시킨 과설계. |
| 변화 대응 | 미흡 | 핵심 방향이 "외부에서 상태 바꾸기"인데, 전환 트리거가 `Test_OnInputPressed`(콤보 if-else)·`CheckAutoTransition`(스왑맵)으로 매니저에 하드코딩됨. AI가 요청할 입구가 없다. |
| 낮은 결합 | 나쁨 | `PlayerStateManager`가 스왑·입력·애니맵·상태생성·이벤트를 다 직접 안다. "스왑은 별개" 목표와 정반대. |
| 책임 분리 | 나쁨 | 매니저 하나가 싱글톤·주입해체·상태생성·스왑전환·콤보규칙·자동전환을 다 한다. 전환 엔진을 넘어 게임 규칙까지 떠안음. |
| 테스트 | 나쁨 | 싱글톤 + 실제 Animator 직접 호출. 가짜를 못 끼워 상태 진행 로직을 단독 테스트 불가. |
| 디버깅 | 보통 | 진행률 흐름은 한곳(`CharacterBaseState.UpdateState`)에 모였으나, 전환 트리거가 곳곳에 흩어짐. |

## 축 2 — 객체지향적인가

| 기준 | 판정 | 근거 (문제 위주) |
|------|------|------|
| 캡슐화 | 보통 | 상태 내부값(`_readIndex`, `IsFinished`)은 숨겼으나, `nextStateKey`가 `protected` 날 필드라 직접 대입으로 전환을 일으킴. 통로(메서드)가 아님. |
| 책임 분리 | 나쁨 | 스왑·입력·콤보가 한 객체에 뭉침. |
| 느슨한 결합 | 보통 | 주입은 인터페이스로 받지만 `Test_OnInputPressed`가 `PlayerStateType` 구체값에 직접 의존. Enemy엔 그 enum이 없어 못 씀. |
| 다형성 | 미흡 | 상태는 `CharacterBaseState`로 다형성을 살렸지만, 전환 규칙은 if 떡칠. 콤보 늘면 if 증가. |
| 의존성 주입 | 보통 | 밖에서 받긴 하나 `Activator.CreateInstance`로 매니저가 직접 생성 + 싱글톤(`_instance`) 전역노출로 스스로 원칙을 깸. |

## 핵심 결론

**제네릭이 헛돈 진짜 이유 = "캐릭터 스왑"을 상태 시스템 안에 넣었기 때문.**

- `ECharacter` 제네릭, `_characterSwapMap`, `OnCharacterSwapped`가 매니저에 박혀서,
  상태 시스템이 "캐릭터가 1개냐 2개냐"를 알아버렸다.
- 그래서 스왑이 없는 Enemy엔 이 제네릭이 의미 없고, Player에만 맞는 코드가 됐다.

**스왑을 떼어내면** 상태 시스템은 `BaseState<EState>` 하나로 충분해지고(캐릭터 제네릭 불필요),
제네릭이 비로소 Player/Enemy/보스에 재사용된다.

→ **재설계 가능성: 충분. 스왑을 상태 시스템 밖으로 빼는 것이 핵심 한 수.**

## 우선순위

### 지금 고칠 것
1. 매니저에서 **스왑 로직 분리** — 스왑은 외부 객체가 하고, 상태 시스템엔 "이 상태로 전환 요청" 공개 메서드(`RequestTransition(EState)`)만 남긴다. (AI도 이 입구로 들어온다)
2. `nextStateKey` 직접 대입 → **전환 요청 메서드**로 캡슐화.
3. 콤보 if-else(`Test_OnInputPressed`) → 상태별 전환 규칙으로 이동(전환을 상태가 알게).

### 나중에 봐도 될 것
4. `ECharacter` 제네릭 제거 여부 (스왑 분리하면 자연히 사라짐 — 1번 끝나고 판단).
5. 싱글톤(`_instance`) 제거 — 테스트 용이성용. 당장 동작엔 지장 없음.
6. Animator 직접 호출을 인터페이스로 감싸 상태 단독 테스트 가능하게.
