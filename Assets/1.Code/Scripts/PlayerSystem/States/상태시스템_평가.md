# 상태시스템(States) 평가

평가 대상: `Assets/1.Code/Scripts/PlayerSystem/States`
관련 의존: `BaseStateData`(DataSystem), `PlayerStateEventChannel`, `IInputEventProvider`, `ICharacterSwapNotifier`

## 전체 흐름 (코드에서 역추적)

`Awake`(Animator/Data 맵 구축 → Swap 구독 → Activator로 전 State 생성 → 첫 State 지정)
→ `Start`(Input 구독 → CurrentState.EnterState)
→ `Update`(nextStateKey 변경 감지 시 Transition → CurrentState.UpdateState → CheckAutoTransition)
→ `UpdateState`(애니 진행률 추적 → 진행률 도달 이벤트를 EventChannel로 발행)
→ `ExitState`(readIndex 리셋 → RaiseReset)

## 4-1. 판정표

| [좋음/나쁨] 핵심 질문 | 이유 + 피드백 |
|-----------|--------------------|
| **[나쁨]** 시스템 전체 흐름이 한 문장으로 정의돼 있나 | 흐름을 적은 주석이 없다. `StateManager` 클래스 주석은 `// FSM 구`에서 잘려 있다. 흐름이 코드 여러 곳(Manager Awake/Update + BaseState UpdateState)에 흩어져 한 줄로 안 잡힌다. |
| **[좋음]** 각 클래스·메서드가 한 줄로 설명되나 | 주석은 부족하나 이름이 역할을 드러낸다(EnterState, TransitionToState, CheckAutoTransition). 단 `Test_OnInputPressed`는 임시 성격. |
| **[나쁨]** 일관된 코드 규칙을 따랐나 | 필드 네이밍이 섞임: `states`, `nextStateKey`(접두사 없음) vs `_instance`, `_stateDataMap`(언더스코어). `CharaterAnim` 오타. |
| **[좋음]** 변수명이 읽기 쉬운가 | 대체로 의도가 드러남(nextInfo, progress, _sortedEvents). 단 `CharaterAnim` 오타는 수정 필요. |
| **[나쁨]** 함수 길이가 적절한가 | 대부분 짧으나 `UpdateState`가 전환판정+진행률계산+이벤트발행을 한 메서드에 담아 길고 분기가 깊다. `Awake`도 5가지 일을 한다. |
| **[나쁨]** 지금 요구에 비해 과한 구조가 없나 | `CanReenter` 프로퍼티는 정의만 되고 어디서도 사용 안 됨(죽은 코드). 제네릭 2개(EState, ECharacter)인데 구현체는 Player 하나뿐 — 현재는 과추상. |
| **[나쁨]** 같은 일을 더 짧게 쓸 수 있나 | `Test_OnInputPressed`의 콤보 분기가 중복(매번 TryGetValue + CurrentState 비교 반복). 데이터/전이표로 줄일 수 있다. |
| **[나쁨]** 함수가 역할대로 분리돼 재사용되나 | `UpdateState`에 전환감지·진행률·이벤트발행이 엉켜 일부만 떼어 쓸 수 없다. |
| **[나쁨]** 주변을 가짜로 갈아끼워 따로 테스트되나 | BaseState는 Animator를 주입받아(좋음) 일부 격리 가능하나, Manager는 `Activator.CreateInstance`로 State를 내부 생성 + 싱글톤(`_instance`)이라 격리 불가. |
| **[나쁨]** 문제 생겼을 때 흐름 추적이 쉽나 | 이벤트가 ScriptableObject 채널을 거쳐 간접 발행돼, 누가 받는지 코드로 따라가기 어렵다. |
| **[좋음]** 핵심만 빼고 나머지 없어도 도나 | `CreateStates`에서 anim/data 없는 State는 `continue`로 건너뛴다. 비핵심 누락에 견디는 구조. |
| **[좋음]** 매 프레임 도는 연산이 가벼운가 | UpdateState는 진행률 비교 + 도달 이벤트만 처리해 가볍다. O(n^2) 없음. |
| **[좋음]** 런타임에 GC 스파이크를 안 만드나 | 런타임 경로에서 할당 적음. 단 `GetData<T>`는 호출마다 new Dictionary 생성, `EnterState`의 `#if UNITY_EDITOR SortEvents`는 에디터에서 진입마다 할당(런타임 영향 없음). |
| **[좋음]** 동시 수가 늘어도 견디나 | State 수에 선형. 전수탐색·중첩루프 없음. |
| **[나쁨]** 더 빠르게·가볍게 고칠 여지가 없나 | `GetData<T>` 결과를 캐시하면 반복 생성 제거 가능. SortEvents도 Initialize 1회로 충분. |
| **[나쁨]** 한 객체가 한 책임만 지나(SRP) | `PlayerStateManager`가 맵 구축·Swap 구독·State 생성·싱글톤·Input 테스트·콤보 로직을 모두 가짐. `CharacterBaseState`도 애니 추적 + 이벤트 정렬/발행 두 이유로 바뀐다. |
| **[나쁨]** 새 종류 추가 시 기존 코드를 안 고치나(OCP) | 새 State 추가는 클래스+enum만으로 자동 등록(좋음)이나, 콤보 전환은 `Test_OnInputPressed` if-else에 박혀 새 공격마다 수정해야 한다. |
| **[좋음]** 자식이 부모 자리에 들어가도 규약이 안 깨지나(LSP) | State 자식들이 부모 계약(StateKey/AnimationName 등)을 그대로 채워 치환 가능. 예외·빈 throw 없음. |
| **[좋음]** 안 쓰는 멤버까지 강요받지 않나(ISP) | Raiser/Subscriber 인터페이스가 발행/구독 역할별로 분리됨. |
| **[나쁨]** 객체끼리 약속(인터페이스)으로 연결되나(DIP-결합) | Input/Swap은 인터페이스 의존(좋음)이나, `_eventRaiser`는 구체 타입 `PlayerStateEventChannel`을 직접 주입받는다. |
| **[나쁨]** 필요한 것을 밖에서 받아오나(DIP-주입) | `[Inject]`로 다수 주입(좋음)이나, State 인스턴스는 `Activator.CreateInstance`로 내부 조달 + 싱글톤 자기노출(`_instance`). |
| **[좋음]** 내부 상태를 숨기고 통로로만 다루나(캡슐화) | Manager 필드는 private, 베이스의 IsFinished 등은 private set. Inspector 직접 노출 없음. |
| **[나쁨]** 같은 약속을 여러 구현이 다르게 채우나(다형성) | State 다형성 골격은 있으나 개별 State는 프로퍼티만 다른 빈 클래스라 행동 차이가 없고, 전환은 if-else로 처리. |
| **[나쁨]** 씬 바뀔 때 잔존·누수·에러 없이 정리되나 | `PlayerStateEventChannel`은 ScriptableObject라 씬을 넘어 잔존 — 구독 핸들러가 해제 안 되면 누수. 싱글톤 `_instance`는 정적 참조. |
| **[나쁨]** 같은 코드·지식이 여러 곳에 중복되지 않나(DRY) | HIdle/AIdle/HNormalAttack1~3가 거의 동일한 프로퍼티 4종 보일러플레이트를 복붙. (State 패턴 특성상 일부 불가피하나, 데이터 주도로 줄일 여지 있음.) |
| **[좋음]** 바로 옆 객체만 알고 내부까지 안 파고드나(LoD) | `character.GetCharacterComponent<Animator>()` 등 한 단계 접근. 깊은 a.b.c.d 체이닝 없음. |
| **[좋음]** 상속 대신 부품 조합으로 짜나 | 상속 계층이 1단(BaseState→구체)으로 얕고, 기능은 이벤트 채널 조합으로 붙인다. |
| **[나쁨]** 이벤트 구독과 해제가 짝이 맞나(유니티 함정) | Swap 구독은 OnDestroy에서 해제(짝 맞음). 그러나 `_inputBroadcaster.OnInputPressed += Test_OnInputPressed`(Start)는 해제 코드가 없어 누수·다중 발동 위험. |
| **[좋음]** 코루틴·async가 정리되나 | 코루틴/async 미사용. 해당 없음. |
| **[좋음]** 파괴된 객체와 진짜 null을 구분하나 | `CurrentState == attack1` 등은 일반 객체 참조 비교로 안전. Unity null 함정에 빠지는 비교 없음. |
| **[나쁨]** static·싱글턴이 씬 객체를 붙들어 누수 안 만드나 | static `_instance`가 씬의 Manager를 참조. DontDestroyOnLoad는 없으나 싱글톤 패턴 자체가 정적 수명 관리 부담을 만든다. |

## 4-2. 문제와 개선 방향

### 좋은 점 (유지/강화)
- **자동 등록 구조**: `Activator` + `[InjectSubTypes]`로 새 State를 클래스·enum 추가만으로 등록 — 확장 시 등록 코드 수정 불필요. 콤보/전환 로직도 같은 수준으로 데이터 주도화하면 OCP가 완성된다.
- **인터페이스 분리(ISP/DIP 일부)**: Raiser/Subscriber, Input/Swap 알림이 역할별 인터페이스로 나뉘어 결합이 느슨하다. 재설계 시 이 경계는 그대로 살릴 가치가 있다.
- **누락 견딤**: `CreateStates`의 `continue` 처리로 일부 데이터가 없어도 전체가 멈추지 않는다.

### 문제·단점 (개선 방향과 함께)

1. **`PlayerStateManager`의 SRP 붕괴 (가장 시급)**
   `Awake` 하나가 Animator 맵·Data 맵·Swap 구독·State 생성·싱글톤·콤보 로직까지 떠안는다. 바뀌는 이유가 6가지라 한 곳을 고치면 다른 데가 깨진다.
   → **개선**: ① 맵 구축은 별도 초기화 객체(또는 빌더)로 분리, ② 콤보/전환 규칙은 Manager 밖의 "전이 규칙(Transition Table)" 객체로 빼낸다, ③ 싱글톤은 DI로 대체(아래 4번).

2. **콤보 전환이 if-else 하드코딩 (OCP·다형성 위반)**
   `Test_OnInputPressed`가 공격 단계를 if-else로 직접 비교한다. 새 콤보·캐릭터(A 캐릭터 공격)를 넣으면 이 분기를 계속 수정해야 하고, 메서드 이름도 `Test_`로 임시다.
   → **개선**: `(현재 State, 입력) → 다음 State` 전이표를 데이터(딕셔너리/SO)로 정의. 발사는 표 조회 한 줄로 끝나고, 추가는 표에 행만 넣으면 된다.

3. **`UpdateState` 책임 혼재 (재사용성·디버깅)**
   전환 감지·진행률 계산·이벤트 발행이 한 메서드에 엉켜 있어 일부만 떼어 테스트하거나 재사용할 수 없다.
   → **개선**: `진행률 계산`과 `진행률 도달 이벤트 발행`을 분리. 전환 종료 판정(IsFinished)도 별도 메서드로.

4. **`Activator` + 싱글톤 (테스트성·DIP·정적 수명)**
   State를 내부에서 `Activator.CreateInstance`로 만들고 `_instance` 싱글톤을 자기노출한다. 격리 테스트가 불가능하고, static이 씬 객체를 붙든다.
   → **개선**: State 생성도 DI 컨테이너/팩토리로 주입. 싱글톤이 꼭 필요하면 수명 주체를 명확히(씬 한정 or DontDestroyOnLoad 일관) 하고, 가능하면 주입으로 대체.

5. **Input 구독 해제 누락 (누수)**
   `OnInputPressed += Test_OnInputPressed`만 있고 `-=`가 없다. 씬 재진입·재생성 시 핸들러가 중첩 구독돼 입력 한 번에 여러 번 반응할 수 있다.
   → **개선**: `OnDestroy`(또는 OnDisable)에서 `-=` 해제. Swap 구독처럼 짝을 맞춘다.

6. **ScriptableObject 이벤트 채널의 잔존 위험 (씬 전환)**
   `PlayerStateEventChannel`은 SO라 씬을 넘어 살아남는다. 구독 핸들러가 해제되지 않으면 죽은 객체를 참조한 채 발행돼 누수·오발동 위험.
   → **개선**: 구독자 측 OnDisable 해제를 강제하고, 씬 전환 시 채널 초기화 지점(이미 있는 `OnEnable` 리셋과 짝)을 둔다.

7. **`GetData<T>` 반복 할당 / `CanReenter` 죽은 코드 (간결성)**
   `GetData`는 호출마다 Dictionary를 새로 만든다. `CanReenter`는 정의만 되고 미사용.
   → **개선**: `GetData` 결과는 1회 캐시, `CanReenter`는 실제 재진입 제어에 쓰거나 삭제.

8. **네이밍·오타 일관성 (가독성)**
   필드 접두사가 섞이고(`states` vs `_instance`), `CharaterAnim` 오타가 있다.
   → **개선**: 필드 네이밍 규칙 통일(예: private는 `_camelCase`), 오타 수정.

### 재설계 시 우선순위 제안
1순위: 1·2·4 (구조 골격 — SRP/전이표/DI). 재설계의 핵심.
2순위: 3·5·6 (메서드 분리·누수). 구조 잡힌 뒤 정리.
3순위: 7·8 (할당·네이밍). 마무리 단계.
